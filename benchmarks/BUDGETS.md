# Perf budgets, with the numbers and what asserts them

Generated by `python3 tools/gen_budgets.py write` from `tools/gen_budgets.py` — the one source
of every threshold in this repository. Do not edit this file; edit the generator, whose rationale
fields carry where each number came from, and run
`python3 tools/gen_adr_tables.py write` so ADR-004 §11 renders from the same table. A budget
that exists in two places is a budget that drifts, and a drifted budget is a budget nobody fails
on (ADR-004 D14).

Every number below is a budget id: `<family>.<size_class>` — so `cold.index.ms.small` is the
`cold.index.ms` family at the `small` size class. **192 numbers, 48 families, 4 size classes.**

## What runs, and where the numbers come from

| command | what it does |
|---|---|
| `make bench` | build the release binary, run the scripted end-to-end benchmark over the `small` fixture corpus, run the criterion benches, calibrate the runner, print the verdicts |
| `make bench-check` | the same, in CI mode: also enforces the 15 % regression gate against `benchmarks/baselines/perf-gate.json` and that every measured number has a blessed baseline |
| `make bench-bless` | rewrite the baseline from this run — the ratchet. An improvement past 15 % fails until it is blessed, because a baseline nobody re-blesses is a budget nobody tightens |
| `make bench-selftest` | prove the gate can fail: no build, no fixture, synthetic numbers only |
| `make bench-criterion` | just the criterion benches (`crates/fathom-store/benches/budgets.rs`) |

The gate reads its rules out of `benchmarks/budgets.json`'s `gates` key rather than restating
them, so this table is the rules as they are enforced today:

| gate rule | value | what it means |
|---|---|---|
| `regression_fail_pct` | 15 | a measured number more than this past the blessed baseline is a red build, and so is one better than it: budgets ratchet |
| `improvement_baseline_commit_required` | `True` | an un-blessed improvement is a failure, so a fast commit has to be made fast *on purpose* |
| `runner_calibration_factor_range` | `1, 4` | the runner factor is clamped into this window; a machine outside it says so instead of handing out a pass |
| `runner_calibration_bench` | `calibrate: 100k-row batched insert + 10k FTS queries` | the workload the factor is measured on, run at gate time (`tools/perf_gate.py`) |
| `rss_budgets_scaled_by_factor` | `False` | memory budgets are never scaled by the machine: a slow runner is not allowed to grow the resident set |
| `skip_xlarge_below_ram_mib` | 8192 | the `xlarge` class is skipped below this much RAM — and the skip is printed, never silent |
| `skipped_budgets_must_be_reported` | `True` | every budget the gate did not assert is listed in the report and on the terminal |

A wall-clock budget gets the runner factor as headroom at gate time; the baseline comparison
divides the measurement by the same factor to bring it back to the reference machine's units.
Both use one factor, measured on the machine running the gate, which is what makes a timing on a
CI runner comparable to a timing on a laptop (ADR-004 §11.8).

## Recorded breaches

A budget that currently fails is not deleted from the page and is not quietly green: it is
listed here with the defect that owns it, the ceiling it may not grow past and the date the
grace runs out. The gate fails the moment one of these grows beyond its ceiling; the ledger
in ADR-004 §11.10 is the same table, and `tools/epic7_acceptance.py` fails the epic if a row
has stopped biting or an expiry has gone by. An entry is removed by hand when the defect
closes — which is when the budget starts gating again.

| measurement | budget | ceiling | owner | expires | why |
|---|---|---|---|---|---|
| `store.bytes_per_commit_spine.small` | 4,096 | 10,500 (1.15 × tolerance) | `reco-7yq` | 2026-12-15 | the harness bills every non-cache table to a budget whose byte model is the commit tables: on this corpus at the epic's close `graph_*` is 6,865 B/commit of the ~8,275 measured (49.8 % of the store is the graph lane), while `git_commit` + `git_commit_file` + `ref_tip` are 1,376 B/commit. The number also moves with how much of the lane one gate run happens to write (8,289 at 3 samples, 10,446 at 5), which is the same defect talking. ADR-004 §11.6 gives the lane its own budget (`store.bytes_per_commit_graph`, 32 KiB/revision) and `perf_gate.py` has never measured it. ADR-004 §11.10; delete this row when reco-7yq gives `store_split` the ADR's three denominators. |
| `warm.reindex.ms.small` | 150 | 1,750 (1.25 × tolerance) | `reco-r3x` | 2026-12-15 | the run is not a warm re-index, it is a graph backfill wearing one: a cold index leaves `graph.window`-sized debt (340 owed revisions on this corpus), and the next ten runs each settle 32 of them at ~1 s. At rest the same measurement is ~100 ms (`episodes` 46-54 ms, `graph` ~40 ms) and passes the 150 ms budget. Measured and written up in ADR-004 §11.10; delete this row when reco-r3x closes. |
| `warm.reindex.noop.ms.small` | 10 | 1,250 (1.25 × tolerance) | `reco-r3x` | 2026-12-15 | a run that reports `nothing_new: true` still runs the graph backfill, so §6.6 R1's ~1 ms store-side no-op costs ~1 s until the owed list empties (then it is 2-4 ms). The budget is right and the run is wrong; `reco-7tc`'s no-op is intact once the lane is at rest. ADR-004 §11.10; delete this row when reco-r3x closes. |

## Proving the gate can fail

A gate nobody has seen fail is decoration. Two ways to see it fail:

```text
python3 tools/perf_gate.py --self-test                 # no build, no fixture: the arithmetic
python3 tools/perf_gate.py --check --inject-ms 400     # the deliberate regression, for real
```

`--inject-ms` puts a real `sleep` in front of every measured process, so the cold index, the
warm re-index, the no-op re-index and the card read all inherit it; the gate must go red (exit
11, `BUDGET_EXCEEDED`) and name each budget it blew. `tests/test_perf_budget_contract.py` runs
both and fails if the gate is ever unable to fail.

## Where the trend lives

`benchmarks/trend/` — `trend.jsonl` (one line per run), `trend.md` (the rendered history),
`latest.json` (the full report). It is a **CI job artefact and is gitignored**, deliberately: a
committed timing file is a merge conflict on every PR, and a merge conflict on every PR is how a
trend file stops being updated. The committed number is the baseline, and the only thing that
rewrites it is `make bench-bless`.
