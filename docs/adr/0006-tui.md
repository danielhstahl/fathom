## 0. Why this document exists, and what it decides

Screens get built before anyone decides what they are, and the cost is paid by the user in
the only currency they have: the eleven keystrokes it takes to answer a question they should
have been able to answer with two. `e1.5`, `e1.6`, `e1.7`, `e4.5`, `e5.1`…`e5.6` are all
*screen* tickets, and eleven screen tickets with no shared contract produce eleven
applications: eleven motion models, eleven ways of shrinking, one key bound five times, and
"press `?`" shipping a help overlay that describes a keymap nobody implemented.

This ADR decides five things, and each is checkable rather than aspirational:

| # | Decision | Where | Checked by |
|---|---|---|---|
| 1 | **Nine views**, each with a pane layout, a focus ring and named drill edges | §4, §5 | `test_every_view_has_a_layout_focus_ring_and_drills` |
| 2 | A **sizing contract**: every view is complete at 80×24, and `min`/`floor`/`refuse` are arithmetic, not opinion | §3 | `test_every_view_is_complete_at_80x24` |
| 3 | **One degradation ladder**, applied in one order, announced on screen when it fires | §6 | `test_degradation_is_an_ordered_ladder_not_a_vibe` |
| 4 | **One keymap** with a mode model, a rule against view modes stealing navigation keys, and a chord list the terminal cannot deliver | §7, §8 | `test_default_keymap_is_conflict_free`, `test_no_mode_shadows_the_globally_reserved_keys` |
| 5 | **Three canonical tasks** whose exact keystrokes are published and resolved through the real keymap | §9 | `test_canonical_task_sequences_resolve_as_published` |

The generated tables in this document are rendered from `src/recommender/tui/`
(`python3 -m recommender.tui doc --check` fails CI on drift, like `e0.8`'s config reference
and ADR-004's storage tables). The reason is not tidiness: §7's table is the *source* of the
help overlay (`e1.5`), the palette labels (`e5.4`) and the docs cheatsheet (`e7.5`), and
three hand-copied copies of a keymap is three chances for the help overlay to lie.

### 0.2 New vocabulary

A per-screen ADR needs nouns the thesis does not have. Per ADR-001's rule ("new nouns enter

`tools/check_docs.py` fails the build if any of them is defined twice, which is the mechanical

## 1. The frame model

```
┌ tab bar ── pinned views; `J`/`K` cycle, `<C-w>1..9` jump, `T` pins this view ── chrome
│ the one live view, which owns every remaining row
├ status line ── epoch · counts · the degradation notice · chrome (never dropped)
└ hint line ── the next likely actions, `e5.4`; chrome, dropped first
```

| Noun | Meaning | Never means |
|---|---|---|
| **frame** | The whole terminal: chrome rows plus exactly one live view. | A pane; a browser frame |
| **chrome** | The frame's non-content rows: tab bar, status line, hint line. | The header of a pane |
| **view** | A full-frame way of answering one question. Nine of them (§4). | A pane, a widget, a screen of a multi-screen app |
| **pane** | A bordered region inside a view with its own focus position and its own data. | A view; a tab |
| **focus ring** | The ordered list of a view's panes. `<Tab>`/`<C-w>l` walk it, pane 1 is where focus lands on entry. | Tab order of a web form |
| **drill stack** | The push-down history of (view, pane, selection). `<Enter>` pushes, `<Esc>` pops one, `<C-o>` walks the whole history back. | Browser history; a back button that forgets the model |
| **overlay** | A floating view (`/` search, `,` palette, `?` help, `-` reason chooser) that borrows the frame and leaves the view behind it untouched. | A new view; a modal that destroys context |
| **mode** | The keymap layer that is live (§7.1). Exactly one interaction mode and one view mode, over `global`; `prompt` and `pick` are exclusive. | Vim's insert/normal split, which this deliberately does not copy |
| **tab** | A pinned (view, scope, filters, selection) tuple. `T` pins, `J`/`K` cycle, `<C-w>c` closes. Tabs are *contexts*, not documents. | A file buffer; a terminal tab |
| **scope** | The episode or episode range every view in the frame is currently answering about. `m` marks an endpoint, `c` compares with it (`e5.3`). | The current directory |

Three structural rules:

**R1 — one live view, no split views.** The frame holds exactly one view. Two views side by
side at 80 columns is two unreadable views; the way to see two things at once is to change
the *scope* (`c` for compare, `e5.3`), not the frame. The one exception is inside a view:
the diff's split/unified toggle (`\`) splits a *pane*, and it is opt-in and needs ~100
columns, below which it degrades back to unified (§6.3).

**R2 — focus is lateral, drill is vertical.** `Tab`/`<C-w>h`/`<C-w>l` move focus between
panes without changing the scope; `<Enter>` pushes a drill, which changes what the scope
*is*. This is the distinction that makes `Esc` predictable: `<Esc>` pops exactly one push,
and it never quits the application. The only quit chord is `<C-c>` (§8.1).

**R3 — every pane's content is ordered by decreasing importance.** The layout engine drops
content from the end of a pane when the terminal shrinks (§6). A pane whose most important
fact is at the bottom loses that fact first, which is why the ordering rule is a contract on
`e1.6`/`e1.7`/`e2.10` and not a rendering detail. The test suite enforces that no mock line
exceeds its pane's documented width, so a layout in this document cannot be a wish.

### 1.1 Modes, precedence, and why `prompt` wins outright

<!-- BEGIN GENERATED: modes -->
| Mode | Kind | Exclusive | Live when |
|---|---|---|---|
| `prompt` | interaction | yes | A one-line text field owns the keyboard (search query, palette filter, reason text, path). Everything typed is text. |
| `pick` | interaction | yes | A single-key chooser is open (dismiss reason, snooze window, format). One keystroke chooses; there is no text entry. |
| `list` | interaction | no | A list pane has focus: queue worklist, episode rail, file tree, dependency table, search results, treemap rows. |
| `body` | interaction | no | A content surface has focus: hunk view, episode card, graph canvas, artefact preview. |
| `queue` | view | no | The attention queue is the live view. |
| `timeline` | view | no | The timeline (episode rail + card) is the live view. |
| `diff` | view | no | The diff view is the live view. |
| `structure` | view | no | The structure treemap view is the live view. |
| `graph` | view | no | The module graph view is the live view. |
| `deps` | view | no | The dependency view is the live view. |
| `artefact` | view | no | The export-preview view is the live view. |
| `ambient` | view | no | Ambient mode is the live display mode. |
| `global` | root | no | Live whenever a non-exclusive mode is not holding the key. Owns view switching, overlays, review actions and the frame. |
<!-- END GENERATED: modes -->

`prompt` and `pick` are **exclusive**: while a text field or a chooser owns the keyboard,
`global` does not fire. Without this, typing `queue` into the search box would visit four
views. The cost is that `<C-w>` (delete-word in readline) is not the focus prefix inside a
prompt, so `prompt` binds it to `prompt.delete_word` and the frame prefix is unavailable
there — the price of being able to type the letter `w`.

Precedence is `prompt → pick → list → body → <view> → global`, first binder wins. A view
mode may add keys; it may not steal the navigation keys (§7.2 K4).

**One motion, wherever it lands.** The list-motion actions (`list.down` … `list.last`) have exactly
one implementation — `motion_target` in `fathom-tui/src/app.rs` computes the target row from the list's
own geometry — and it is shared by every pane that shows rows, by both boxes' result lists, and by the
comparison panel (§5.3). "Middle of what is on screen" is therefore the same arithmetic in a worklist, a
palette of 60 actions and a 400-line diff; `crates/fathom-tui/tests/motion_parity.rs` fails when a
surface drifts from it, and `every_view_resolves_the_motion_chords_to_the_same_actions` fails when a
view rebinds one chord to something else. What exclusivity forces is only the *reaching*: in `prompt`
the letters type, so the box walks with `<C-n>`/`<C-p>`, `<Tab>` and the arrows (§5.8, §7.5).

## 2. Decisions at a glance

| Area | Decision | Rejected alternative |
|---|---|---|
| Home view | **Queue** (`q`): ranked worklist first, timeline second | Timeline-first (rejected: ADR-001 §4.1 "the queue is the job", and rank beats chronology for a reviewer with 400 unread episodes) |
| Views | **Nine**, fixed list (§4) | One mega-view with tabs; a per-detector view (rejected: detectors are *content* of the card, `e4.3`) |
| Pane count | **Two panes + chrome** per view at 80 columns; a third region is a strip line inside a pane, never a third column | Three columns at 80 (rejected: 24-column panes are unreadable, and the strip degrades cleanly) |
| Motion | One shared list-motion implementation, bound in the `list` mode, used by every list | Per-view motion (`e5.4`'s AC makes this a test, not a preference) |
| Vim compatibility | **List motions yes, editing verbs no**: `j k H M L gg G <C-d> <C-u>`; `d s g p a x f z c i m` are Fathom's, so vim's `d`/`p`/`a`/`s`/`x` are unavailable, and so are `gt`/`gT` because `g` opens the graph view | Copy vim wholesale (rejected: the ticket's key list *is* the product, and a `g` that waits 500 ms for a second key would make the graph view feel broken) |
| Alt/Meta chords | **Never bound** | `A-j` etc. (rejected on measured grounds: they arrive as `ESC` + key, §8.1) |
| Quit | `<C-c>` only, with `ISIG` left on so the exit hook owns terminal restoration | A `q`-to-quit binding (rejected: `q` is the queue, and a quit key next to eight view keys is a data-loss machine) |
| Mouse | Additive only: click selects and focuses, wheel scrolls, nothing exists only on the mouse | Mouse-first affordances (rejected: ADR-001 §2, keyboard only) |
| Search and palette | Same mechanism, two intents: `/` is content, `,` is commands | One box for both (rejected: the palette must enumerate actions *completely*, and mixing content into it makes completeness unverifiable) |

## 3. The sizing contract

Four numbers per view, three of them derived:

| Name | Meaning | How it is produced |
|---|---|---|
All four are **frame** sizes — chrome included — so that a reviewer can measure them
against a real terminal with `stty size` and get the same answer the table gives.

| Name | Meaning | How it is produced |
|---|---|---|
| **ideal** | The documented size this ADR draws the layout at. Chosen so it is ≤ 80×24, because the layouts in §5 must be readable on the machine the reviewer is already SSH'd into. | Declared per view in `views.py`; `test_drawn_layouts_fit_their_documented_size` proves the drawing matches |
| **min** | The smallest size at which the *documented pane set* still renders, every pane at its documented minimum width. | `Σ pane.min_cols + gutters + frame`, derived in `render.min_cols_view`; rows declared as `min_rows` |
| **floor** | The smallest size the documented pane set can be squeezed to, i.e. after the whole ladder has fired and before any pane is dropped. | `min − Σ ladder recovery`, clamped at the single-pane floor (`render.floor_cols`) |
| **refuse below** | Below this the view is not drawn at all: the refusal panel replaces it (§6.6). | Columns: the primary pane's `hard_min`, taken **without** its frame, because the frame is sold two steps earlier. Rows: the chrome left standing after the ladder (the status line, one row) plus the view's own content floor |

Read three things off that table:

1. **Every view is complete at 80×24.** The `min` column is below 80×24 everywhere, and the
   layouts in §5 are drawn at the ideal size. `e5.5`'s matrix (80×24, 100×30, 120×40,
   160×50, ultrawide, 40×10) is asserted in §6.5.
2. **Ambient has the smallest floor**, and it is the only view whose floor is stated in
   ADR-001 rather than derived here: §4.1 promises ambient fits a 40×3 tmux pane, so ambient
   declares a 40-column line budget and two content rows (§5.7), and `refuse_below` reads
   40×3. That is the promise paid for rather than restated. ADR-001 §4.1 also says ambient
   fits 80×12, which the table shows with room to spare.
   narrow tmux pane (`e5.1`'s AC) is not an edge case.
3. **`min` is derived.** Nobody can quietly widen a pane and leave the documented minimum
   lying, because the number is arithmetic over the pane table.

Growth above ideal is a rule too, because "it just stretches" is not one: spare columns go
to the primary pane first until it is twice the width of the widest secondary, then split
evenly; spare rows go to the primary pane's content; pane strips never grow. This is what
keeps a 240×60 terminal looking like a considered design instead of a blown-up 80×24.

Ambient is a *display mode*: same model, no chrome. Its declared chrome is the status line

**Amendment (`reco-8bx`, the second half of `e5.1`): the same view as a process.** `fathom ambient` is
§5.7 drawn by a program whose only job is to be open in the other terminal — no tab bar, no frame, no
session to restore, and nothing to do but answer *is there anything I need to look at right now* until it
changes. It keeps this section's contract and adds four of its own. **It is tickless in the §0.1 sense**: it
blocks for one poll (400 ms by default), reads the cheapest facts it can — a `stat` of the store, the
watcher's heartbeat, `HEAD` — and opens the index only when one of them moved, then draws **only if the text
it would print has changed**; ages are bucketed (`now`, `<15s`, `15s`, `1m`) so a repository with nothing
happening in it does not redraw once a second to say the same thing. **Its cost is a checked number, not an
intention**: `fathom ambient --self-check` prints polls, draws and the run's own measured CPU share and exits
**11** over a budget of 1 % of one core, so "it goes quiet" is gated in CI rather than claimed here.
**`<Enter>` is a handover, not a navigation**: the pane exits, names the episode it was showing, and the full
view is opened in the same terminal through the session's own resume door (`tui.view`, `timeline.selection`),
which is also how a `--root` other than the working directory keeps its identity across the keypress.
**And its refusal is drawn, not fatal**: below 40×3 it prints `AMBIENT REFUSED — TOO SMALL`, the size it
needs and the verb that works at any size, and exits **0** — the reviewer made no mistake, and a pane that
tried to draw 80 columns of fact into 30 would be the lie this ADR refuses everywhere else (§6.6).
The machine form follows §6.7 rather than inventing one: `--once` prints the pane as text and the exit code is
the answer, `--json` streams one `fathom.cli.ambient/1` object per change — the same object-per-change shape
`fathom watch --json` uses — and `--plain` means the same thing here as it does everywhere else.

store risk>60 author:dana kind:episode` narrows by the last three and ranks by the first
two. The tokens, printed in the box's own preview pane when the query is empty (this is where
a reviewer reads them, so this is where they are written):

| Token | Means | Notes |
|---|---|---|
| `author:` | who wrote it | substring, case-folded |
| `since:` / `until:` | on or after / on or before a day | `7d`, `yesterday`, `2026-03-01`; a day is a local midnight, never a millisecond window (`until:2026-03-01` includes that day) |
| `risk>` / `risk<` | at least / at most this risky | refused with a sentence when nothing in the corpus carries a score |
| `kind:` | `episode`, `path`, `dependency`, `finding`, `symbol` | narrows the group list rather than the score |
| `path:` | touches this path | also matches the row's own name, which is what a path row's name is |
| `dep:` | depends on this package | |
| `finding:` | raised this finding kind | |

An unrecognised `prefix:value` is **kept as text and said so** rather than dropped: a token the
build cannot honour is a fact about the build, and `fathom` says which. A filter that narrows
nothing at all is reported with its count (`2 of 0 candidates`), because a filter that silently
did nothing is a query whose answer was never about the repository.

**Where the code is.** The corpus, the scorer, the filter grammar and the report are
`fathom_analyze::search` (with `search::score`, `search::query` and the store read in
`search::corpus`); the symbol section is filled by `search::symbols`, which asks `fathom_ingest::worktree`
for the working tree and hands what comes back to the structural extractor of `e3.1` under stated caps —
the analysis crate is IO-free (ADR-002 §3, lint `W1`), so the walk that opens the directory lives at the
door — because a declaration is a function of the tree and not of an episode; the recent and saved searches
are `search::history`, which is deliberately
not a store read so a backend-less binary still remembers what the reviewer was asking. Every corpus
carries the identity it was read from — the store's index epoch and the tree the symbols came from — so a box
that stayed open while the repository moved says so instead of answering from rows the repository has already
replaced. The overlay, its deep links and its rows are `fathom_tui::search`, and the corpus itself is read by
`fathom-cli`'s `search` module at startup and handed over — the shell scores what it was given
and never opens a store (§1 R3, ADR-002 §5.2). The latency promise is ADR-004's
`query.search.ms` (p95 50 ms), measured by `fathom-analyze`'s `tests/search_scoring.rs` on a
ten-thousand-episode corpus, over this same call path — with ADR-004 §11.8's runner factor as headroom,
because that test measures the debug build on whatever runner CI happened to hand it (`reco-cqwz`).

## 6. The degradation contract

The brief asks for "one degradation order per view". This section instead defines **one
ladder for all views**, applied in a fixed order until the view fits, and then *derives* each
view's order from the steps that fire for it. A per-view hand-written list would have been
nine documents that disagree with each other the first time a pane width changes.

### 6.3 Width and height are different problems

Rows degrade by **removing** lines in importance order (§1 R3). Columns degrade by
**narrowing** panes and then by dropping *columns of a row*, in a fixed order per list:
sparkline, relative-time→date, author, then the risk *number*, and finally the risk *glyph*
last of all (§5.2). Diff hunks never drop a column: they truncate the line and print `…`,
because a silently truncated diff line is worse than a visible one. The diff's split view is
opt-in and degrades to unified below ~100 columns rather than clipping a side.

### 6.4 Announce, every time

Dropping content silently is the one failure ADR-001 §7.2 says a review tool is not allowed.
So a degraded frame says so, and the notice **leads** the status line — the status line is
the last chrome standing and the first thing to be truncated, so a notice that could be
clipped away would be the same hidden suppression in a nicer font. These two frames are
rendered by the same code `e5.5` will ship, not typed here:

<!-- BEGIN GENERATED: degradation-notices -->

### 6.6 Below the floor: fall back, then refuse — both stated

Below a view's **floor**, `D9` gives the secondary panes back to the primary pane and the
status line names what left the frame; the content is one `<C-w>l`/`<Enter>` away and the
selection is preserved. Below a view's **refuse** size the view is not drawn at all:
`e1.5` shows a refusal panel that states the size needed, the size it got, the key that
switches to ambient (which fits 40×3), and `fathom --plain` for a text render (`e5.5`).
Drawing a 9-column treemap would be the failure; saying "I cannot draw this here" is the
correct answer to a question the terminal cannot ask.

The panel is `fathom_tui::frame::refusal_panel()`, and it is drawn by the same code that drew
§6.4's notices, because "reported, not silent" has to survive being read. Two things about it
are testable and tested rather than left to review: the width budget (`f "need {want}×{h}, have
{w}×{h}"`, the widest line in the panel, sets the floor's width, so the message cannot be the
reason the panel does not fit), and the ordering — what a `d` on a 25×12 terminal *becomes* is
exactly the sentence an operator needs before reaching for a key.

### 6.7 Non-TTY and pipes

No terminal at all is not a degradation, it is a different contract: `--plain` prints ordered
text with no escape sequences (`e5.5`), and every view has a headless equivalent through the
CLI verbs (`e1.10`). The refusal panel is for a real terminal that is too small; `--plain` is
for no terminal.

Two panes side by side is the right shape for eyes and the wrong shape for anything else, so
`--plain --lines` prints the same frame in **reading order**: one block per pane, each block
headed by the pane's own name and position (`▸ worklist · e4.5 · pane 1 of 2`), with no column
rules and no clipping to a column's width — a `reads …` line that the grid had to ellipsize
arrives in full. Same facts, same order, one per line, which is what makes it usable as a log
and what a screen reader expects. `crates/fathom-cli/tests/tui_text.rs` pins the three claims
that can be checked from outside the process: no `\x1b` reaches stdout, no column rule survives
in the line mode, and every row the grid drew is in the line mode (allowing it to be longer).

The facts about the terminal — `TERM`, `COLORTERM`, `NO_COLOR`, the locale chain, tmux, screen,
ssh, whether stdout is a terminal at all — are gathered by the CLI into a
`fathom_tui::terminal::Probe` and *passed in*, because `fathom-tui` does not read the process
environment (ADR-002 §5): a library that reads `TERM` cannot be driven from a test, a daemon or
a MCP server. `Probe::notices()` is the list of degraded answers, each naming the remedy, and
the CLI prints them on both paths — to stderr under a TUI, to stderr beside the text on a pipe.
A healthy terminal gets none: a wall of caveats trains the reviewer to skip the one that matters.

### 7.0 The four rules

| # | Rule | Why | Checked by |
|---|---|---|---|
| **K1** | Every action is bound in some mode **or** is a palette entry. The palette is a keyboard surface, so "palette-only" is still reachable. | "Everything reachable from the keyboard" has to be a property you can enumerate, not a hope. | `test_every_action_is_bound_or_in_the_palette` |
| **K2** | Every mode's bindings are checked against the action registry: an action bound in a mode that does not accept it is a startup error with the file and line to fix. | `keys.overrides` is user input, and a silently-ignored override is a user who believes a wrong keymap. | `test_conflicts_are_reported_not_absorbed` |
| **K3** | Each of the eight frame views is one letter on the home row neighbourhood, and those eight letters plus `/`, `,`, `?` are reserved globally. | Muscle memory is the whole point of a keyboard-first tool; two letters per view would double the sequence length of every task in §9. | `test_view_keys_match_the_view_registry` |
| **K4** | A view or interaction mode may never shadow a globally reserved key. | `p` inside the graph canvas must still mean "go to deps". A view that eats its own navigation keys is a view with a maze in it. | `test_no_mode_shadows_the_globally_reserved_keys` |

### 7.1 Mode model

`MODES` and `PRECEDENCE` are in §1.1. Two consequences worth stating: the same chord can mean
different things in `list` and `body` (`j` moves a selection vs scrolls a document) and that
is *correct*, because the pane type is the mode; and the two exclusive modes mean a text
field is a genuinely different instrument, not a filter that happens to eat some keys.

**Text means every keystroke the mode does not bind, the space bar included.** The terminal does
not deliver the space bar as a space: it arrives as the chord `<Space>`, and a runtime that
decides "printable" by counting one character excludes it. The consequence of getting that wrong
is total rather than cosmetic, because the query grammar (§5.2) is token-based: a field that
eats the space cannot express `risk>60 author:dana`, let alone the free text that composes with
it, and it then saves the mangled result as what the reviewer asked for. `keymap::text_of` is the
one place that answers "is this chord text?", and the published table (§7.3) binds no action to
bare `<Space>` in `prompt` or `pick` — the space bar is not a key to spend, so nothing has to
choose between the field and an action. (`<Space>` is `list.expand` in `list`, where no field is
holding the keyboard; an override may still spend it in an exclusive mode on an action that mode
is allowed to bind, and then it is the reviewer's own space bar they spent.)

### 7.2 Motion conventions

One implementation (`e5.4`'s AC: "motion behaviour is identical across timeline, file tree,
queue and search results"), bound once in `list`, mirrored in `body` for scrolling, and bound
on the arrow keys as well (`ALIASES` in `keymap.py`; the aliases are bindings, so the
cheatsheet prints them and the test counts them).

```
j / k            one row down / up                <Down> <Up> are the same bindings
H / M / L        first / middle / last visible row
gg / G           first / last row
<C-d> / <C-u>    half page down / up              <C-f>, PageDown, PageUp: full page
<Space>          expand / collapse a node         (tree, treemap, transitive tree)
n / N            next / previous match            (search results, filter hits, changed nodes)
<Enter> / <Right>  drill in                       <Esc> / <Left>  up one level
<Tab> / <S-Tab>  focus next / previous pane      <C-w>h / <C-w>l the guaranteed route
```

What vim does *not* get here, and why: `d`, `x`, `s`, `p`, `a`, `f`, `c`, `m`, `y` are Fathom
verbs (view, reviewed, structure, deps, ambient, flag, compare, mark, copy), so vim's delete,
paste, append, substitute and yank are unavailable by construction. `gt`/`gT` cannot exist
either, because `g` is the graph view and a `g` that waits for a second keystroke would make
the graph key feel broken; tab cycling is `J`/`K` (plus `<C-w>n`/`<C-w>p`, `<C-w>1..9`, and
the palette). This is recorded here precisely so `e5.4` does not relitigate it in a comment
thread at 01:00.

**A held key says so.** `g` is `view.graph` and `gg` is `list.first`, so a lone `g` cannot be
answered until the wait for the second key expires — `CHORD_TIMEOUT`, 250 ms. The cost is
accepted above; what is not accepted is paying it silently. A reviewer who presses `g` and gets
back the same screen presses it again, and the second press is `gg`: a different action, in a
different mode, in a view nobody asked for. So the frame a chord lands on says a chord is in the
air — on the hint row beside the key hints, or on the status row wherever there is no hint row to
borrow (glance has none, and neither has `ui.hints = false`). The line names the key held, what it
becomes if nothing else arrives and how long that will take, and what a second key could still make
of it, all three read out of the merged table so an override cannot make the frame lie about it
(`reco-wlt`). The wait is not shorter; it is no longer invisible. And ambiguity is measured in
keystrokes, not characters: `<` is the first *character* of every named chord and the first
keystroke of none of them, so `<` answers at once and `g`/`gg` stays the one ambiguous pair the
table ships — which is what the paragraph above asserts and what `pending_chord.rs` now measures.

A toast borrows that row; it never owns it. An act's report — what was marked, what was
copied, why a refusal refused — is drawn in place of the hints for `TOAST_LIFETIME`, six
seconds of wall clock, and the frame that gives the row back is drawn whether or not a
keystroke caused it. The lifetime is a clock and not a number of draws because the loop is
tickless: a draw happens when something changed and otherwise nothing is drawn, so a toast
that aged one tick per draw expired only on the next press and never at all on a frame that
had gone quiet — which is the hint line evicted for the rest of a session, from one dismissed
help overlay (`reco-2ll`). The two are never side by side: while a toast is live it *is* the
row, and a reviewer who wants the hints back has nothing to press for them.

A chord in the air outranks a toast, but only for the length of the wait. A toast reports an act
that is already over; a held key is the question being asked right now, and answering it is what
the row is for (§7.2). The loan is still a loan: when the chord resolves to something that prints
nothing, the toast that was there before is back, on its own clock (`reco-wlt`).

## 8. Chords: what the terminal cannot deliver, and what Fathom refuses to bind

Two different lists, and conflating them is how a keymap ends up with a binding that works on
the author's laptop. The first is physics; the second is a promise.

### 8.1 Measured delivery

`python3 -m recommender.tui probe` opens a pty, sets it three ways, and reads what a program
would actually receive: `raw` (crossterm's raw mode), `fathom` (raw **with `ISIG` left on**,
which is the mode this ADR commits to so that the exit and panic hooks own terminal
restoration — `e1.5`'s "Ctrl-C or a panic never leaves the terminal in alt-screen"), and
`cooked` (the inherited default flags: canonical, `IXON`, `ISIG`).

Measured on this container (Python 3.14, `/dev/ptmx` present, `ISIG`/`ICANON`/`IXON`/`ICRNL`
all on by default, `VERASE=0x7f`, `VKILL=0x15`):

| Claim | Result |
|---|---|
| Ctrl-I and Tab are one byte | **confirmed** — `0x09` in all three modes |
| Ctrl-M and Enter collide once `ICRNL` maps CR→LF | **confirmed** — `0x0d` arrives as `0x0a` in cooked mode |
| Ctrl-C / Ctrl-Z / Ctrl-`\` are signals, not bytes, when `ISIG` is on | **confirmed** — no byte reaches the reader in `fathom` mode |
| Ctrl-S / Ctrl-Q are flow control while `IXON` is on | **confirmed** in cooked; Fathom turns `IXON` off, so they *are* deliverable and are simply not bound |
| Meta/Alt is `ESC` + key | **confirmed** — `A-x` arrives as `0x1b 0x78`, i.e. `Esc` then `x` |

Measured again in `e1.5` (`reco-v6t`), because the mode Fathom takes is crossterm's, not the
probe's: crossterm 0.29's `enable_raw_mode` is `cfmakeraw`, and `cfmakeraw` clears `ISIG`. On the
shipped path `<C-c>` therefore arrives as the byte `0x03` and `app.quit` is reached as the binding
the published table says it is, while the `SIGINT`/`SIGTERM`/`SIGHUP` flags and the panic hook are
the second door rather than the only one. Both are tested
(`crates/fathom-tui/tests/terminal.rs`), and neither the promise of this section — Ctrl-C never
leaves the terminal in alt-screen — nor `<C-c>`'s immunity to rebinding depends on which door a
given terminal uses: a terminal that keeps `ISIG` on, including the probe's `fathom` mode above,
is served by the signal path instead.

Two decisions come out of that table. First: **no Alt/Meta chord is bound in v1**, because
`Esc` is the most important key in the keymap and an Alt chord would spend it twice.
Two-keystroke chords (`<C-w>l`, `gg`) are the escape hatch and cost nothing to deliver.
Second: **`<C-c>` is the only quit key**, and it is not a binding at all — `ISIG` stays on so
the panic/exit hook is the thing that restores the terminal, which is exactly what `e1.5`'s
acceptance criterion tests.

### 8.2 Reserved for user override

The first class in the table above is physics. The second class is this ADR keeping keys free
for the user: `<C-a>`, `<C-b>` (tmux and screen prefixes), `<C-e>`, `<C-g>`, `<C-k>`, `<C-n>`,
`<C-t>`, `<C-v>`, `<C-x>`, `<C-6>` and `<S-F1>`. Fathom binds none of them in v1, and `e5.4`
may not "convenience" one later without amending this ADR: the value of a reserved chord is
that a user's `.fathom` config does not break on a minor release.

### 8.3 Overrides, and the merge order

`fathom.toml` carries `keys.overrides.<mode>.<binding> = "<action-id>"` — the `e0.8` key spec
already declares it, and `e0.8` explicitly **refused** a `[keymap]` section that could own
bindings, because the canonical table is this ADR's. Setting a value to `""` or removing the
key unbinds. `keymap.merged()` is the merge, `keymap.conflicts()` is `e5.4`'s startup check,
and the four failure modes it reports are: unknown mode, unknown action, an action bound in a
mode that does not accept it, and a shadowed navigation key (K4). All four are reported at
startup with the offending `file:line`, which is what `e0.8`'s `config explain` machinery
already knows how to produce.

The line is found by reading the file's own text, not the parsed document: `toml_edit` 0.25 hands out
no spans for keys parsed from a string, and a refusal that names the wrong key but no line sends the
user hunting. The lookup is the one a person would do — find `[keys.overrides.<mode>]`, then the
`chord = …` line inside that section — and an override written any other way (an inline table, a
dotted key) is reported with no line rather than with a wrong one. A refused override is *dropped and
said*, never applied: a keymap that half-loads is a keymap whose cheatsheet lies.

`fathom tui conflicts --toml fathom.toml` runs the same check on a file; `--set` is for
one-off questions.

## 10. Mouse, colour, and copy rules that fall out of the layout

### 10.1 Mouse is additive, and only additive

Click selects and moves focus; double-click drills; the wheel scrolls the pane under the
pointer; a pane border drag resizes. Nothing exists only on the mouse, which is checkable in
one sentence: the mouse issues the same actions as the keyboard, so the action registry is
also the mouse's contract, and `e3.4`'s "fully keyboard operable and consistent with the
ADR-006 keymap; mouse is additive" is that sentence made a ticket.

**Capture is opt-in, because the cost is real.** `fathom tui --mouse` takes the pointer; without
it, mouse reports are never enabled, because the instant the terminal starts reporting motion
the terminal's own text selection stops working — and copy is how a reviewer gets a path out of
`fathom` and into a comment (ADR-004 §9). The status line says `mouse on` while it is armed, and
`--plain` refuses it with a sentence rather than ignoring it. `App::pointer` is the whole
implementation, and it is written as a *translator*: a click becomes `Motion(row)`, a second
click in the same cell within the double-click interval becomes `Activate`, the wheel becomes
`Scroll(...)`, and nothing else exists. `crates/fathom-tui/tests/pointer.rs` is the parity
check in the form the claim allows — it applies the gesture and the key to two identical
shells and asserts the resulting state is byte-identical, for every gesture, and that the
keyboard alone reaches every action the pointer can reach. A gesture that lands on chrome
answers in words instead of doing nothing, which is the same rule §6.4 applies to a degraded
frame: an input the terminal cannot honour is a fact the reviewer is owed, not a silent drop.

### 10.2 Colour never carries a fact alone

Risk, added/removed, and violation states each ship a glyph and a text label next to the
colour (`e5.6`'s `NO_COLOR` and colour-blind criteria). This is a layout constraint, not a
theming preference: the glyph is part of the width budget in §5, which is why every pane
table in §5 lists the glyph columns explicitly and why the risk *number* is dropped before
the risk *glyph* when a list gets narrow (§6.3).

Because §10.2 holds, `NO_COLOR` is allowed to be a subtraction and nothing else:
`fathom_tui::style::strip_colour` is the single place a colour is removed, applied at the sink when
the probe answered none. The frame is laid out identically, every glyph, rule and marker stays, and no
cell is painted. `crates/fathom-tui/tests/termenv.rs` checks that by reading the painted cells back
off a real sink, because "the flag is plumbed" and "the flag changes what the terminal is given" are
different claims.

`e5.6` (`reco-2fv`) made the other half of §10.2 measurable, and moved "the single place one is
chosen" from `Face::style` to a **`Theme`**: a view names a face (`Face::Added`), never a colour, and
a test fails the build if a `Color::` literal or a hex appears outside `theme`/`colour`. Built-in
`dark`, `light` and `ansi` are each audited — every face against the ground it is seen on at 4.5:1
(6.0:1 when dimmed), and the added / removed / violation pairs at ΔE ≥ 14 under simulated protanopia
and deuteranopia — with `fathom tui --show-theme` printing the measurements and `--audit` exiting 7 on
a failed floor. Selection is `--theme` > `$FATHOM_THEME` > the *user's* config, and a repository's
`fathom.toml` is deliberately not a layer: a clone does not get to repaint a reviewer's terminal, for
the same reason ADR-001 §4.6 does not trust a clone's consent config. [Theming,
colour-blind safety and colour that is not load-bearing](../concepts/theming.md) is the full contract,
including the screenshot test that draws the timeline twice and asserts the two frames' text is
byte-identical — which is what §10.2 actually claims.

### 10.3 Empty, loading and partial states

Every pane has a named empty state that states the next action (`e5.9`), and every partial
result names its cause and its budget (`e1.10`, ADR-004 §7.6). The generic ones are
fixed here so the copy can be reviewed once as a batch:

| State | Printed | Why this wording |
|---|---|---|
| No index at all | ``no index here yet — run `fathom index` here, then reopen fathom`` | a shrug is not a remedy — and this one is true, because there is nothing indexed to read |
| Index finished, nothing loaded | ``index epoch 1 ready · 500 commits · 412 eps — `t` opens the timeline, which lists them as the index knows them; `fathom show <episode>` prints one in full`` | the index is already done, so the sentence this row used to carry (*run fathom index*) was a loop, not a remedy: the reviewer ran it, reopened the shell, and was told the same thing — the MVP walkthrough's second P1, closed under `e5.9`'s remit. The wording names the timeline because the composition root now reads a page of episodes out of the spine (the walkthrough's first P1): the episodes are readable in this build, and what is still missing is the delta model that ranks them |
| Index finished, nothing to list | ``index epoch 1 ready · 0 commits · 0 eps — the index has nothing to list; `fathom doctor` says whether that is the repository or the run`` | a finished index over an empty repository and a finished index that lost its episodes are different facts, and neither is a quiet repository |
| Index running | `indexing 62 % · ~14 s left (4 102 commits)` | a percentage without a converging estimate is a lie with a spinner |
| Epoch still `building` | ``index epoch 2 building · 500 commits · 0 eps — the epoch is still being written — wait for it; if a rebuild died halfway, `fathom index --rebuild` starts a clean one`` | a rebuild that died is a state with an owner, not an empty repository (`e1.4`, ADR-004 §9.3) |
| Store will not open | ``the index would not open — `fathom doctor` says what is wrong`` | "could not open" and "not indexed" have different remedies, and only `fathom doctor` may decide between them |
| Analysis unavailable | `blast radius: unknown — no graph snapshot at this tree hash` | `unknown` is a value, not a blank (§0.1) |
| Hunk text still decoding | `⋯ hunk 11 (25 row(s)) is being decoded — this window is not complete` + `2 hunk(s) in this window still decoding` | the hunk is on its way from a worker (`e1.8`); the hole sits at the row the hunk starts at so the window neither shrinks nor jumps when it lands, and nothing from another window or another shape is ever drawn to fill it |

Two rules the first four rows and the last two share, both of them learned the expensive way:

* **the index state a pane prints is the index state the caller read.** The shell has no store handle
  and may not get one (ADR-002 §5.2), so `fathom-cli` reads the epoch, its status, and the commit and
  episode counts once, before the first frame, and hands them over. A pane may not guess; guessing is
  how an index of 500 commits got told it was empty.
* **no sentence may name a command this binary does not have.** `fathom --demo` was such a command, in
  this row's old wording; a remedy that cannot be typed is worse than none, because it gets typed.

**Note added by `e5.9` (`reco-2uo`).** Both halves of that rule got built, in that order. `fathom --demo`
is a flag now: the binary carries a miniature repository, indexes it with the ordinary `fathom index`, and
opens on it, which is the one place the tour belongs in a pane — beside `fathom index` in the *no index at
all* row, for a reviewer who has not yet decided whether this is worth setting up. And the rule itself is
machine-checked: `crates/fathom-tui/tests/empty_state.rs` and `tests/empty_views.rs` hold the published
verb and flag list and fail on any pane string that names something outside it, while
`crates/fathom-cli/tests/copy.rs` reads the verb and flag lists off `fathom --help` on the built binary, so
the two lists cannot drift apart unnoticed. The same file requires every refusal to end in a next action.

**Note added after `e1.12`'s MVP walkthrough.** The rule has a second surface, and the walkthrough
found it by measuring the screen instead of reading the code: it redrew after every keystroke and asked whether
anything had changed. Eleven of its forty-one keystrokes had produced no change at all — `y`, `Y`,
`<Enter>`, `x` and `i`, all over an empty rail — while `m` and `w`, a few rows up the same table,
answered in a sentence. A pane with a named empty state beside a key that answers nothing is this
table's failure wearing a different hat, and a keystroke that cannot apply and says nothing is
indistinguishable from a keystroke the terminal lost. So §10.3 covers the keyboard as well as the
panes:

* **every bound action either changes the frame or prints the reason it could not.** The empty rail is
  the state to test in, because that is where a key has nowhere to go: `y` with no path under the
  cursor, `j` with no rows to move over, `<Tab>` in a one-pane view, `t` on the view already live.
* **the reason is the absence and then the way out, in that order** — *nothing is selected, so there
  is no path to copy — `j`/`k` choose an episode first* — the shape this section's other rows use,
  because the second half is the half a reviewer can act on.
* **two ids are exempt, by name and with a stated reason:** `app.quit`, which ends the session rather
  than the keystroke, and `screen.redraw`, for which an identical frame *is* the answer. The
  exemption is re-measured every run, so it cannot quietly outlive its reason.

`crates/fathom-tui/tests/action_speaks.rs` is the enforcement: it walks the whole registry of §7.4
against an empty model in all nine views and fails on any action that neither moved the frame nor
left a sentence on the hint row — the walkthrough's measurement made permanent, for every key rather
than the five it happened to try. A refusal an empty pane already explains does not need a second
sentence: `d` over a rail with nothing in it changes the view and the pane prints why it is empty;
`d` again, in a frame that cannot show the change, is the one that has to speak.

The loading row above is now produced rather than hand-written: `fathom_core::progress` holds one estimator
(a median rate over a window of recent samples, with the rejected alternatives argued in its docs) and prints
`indexing 62 % · ~14 s left · 4 102 / 6 552 commits` identically from `fathom index` and from the shell —
which is what "converging" was ever supposed to mean, and what `crates/fathom-tui/tests/progress.rs` asserts
against synthetic histories whose true per-unit cost is known. Its states are this table's, spelled out in
[docs/concepts/onboarding.md](../concepts/onboarding.md) §3: `estimating…` before a rate exists, `unknown %`
where no denominator does, `stalled` when the counter stops, `done` when it does not stop because it
finished. The per-pane empty states — the same rule applied to nine views rather than to the index axis
alone — live in `crates/fathom-tui/src/empty.rs`, one module, reviewed as one batch.

The loading row above is the visible half of a rule the panes are built on: **a frame is never the
frame that is waiting for a read.** Decoding is done by workers that serve the visible window before
the hunks just outside it, a hard cap bounds what may be in flight, work for a window the reviewer has
scrolled past is cancelled rather than finished, and the neighbour episode is pre-warmed so arriving at
it reads nothing. The mechanism, the caps and the four measured criteria are
[docs/concepts/materialization.md](../concepts/materialization.md); what this ADR fixes is only the
wording of the hole and the fact that a hole is drawn *in place* rather than by redrawing the pane.

## 12. Alternatives considered

* **One view with panels that toggle.** Rejected: at 80 columns, toggling panels inside a
  single view produces a frame whose meaning depends on hidden state. Nine views with a
  shared frame and a shared motion model cost the user nine keys and buy a mental model that
  fits in a cheatsheet.
* **Timeline as the home screen.** Rejected on ADR-001 §4.1: a reviewer arriving to 400
  unread episodes needs a ranking, and chronology is not one. `t` still exists because
  "what happened" is a real question with a different answer.
* **Vim's keymap, faithfully.** Rejected: the ticket's key list is the product. `d` is the
  diff view, so vim's `d` (delete) cannot exist; `g` is the graph, so `gt`/`gT` cannot exist.
  The motions that carry over (`j k H M L gg G <C-d> <C-u>`) are the ones that transfer to a
  read-only tool anyway (§7.2).
* **A modal editing-like command mode with `<Space>` as leader.** Rejected: a leader key makes
  every single-key binding pay a timeout, and single-key view switching is the whole
  interaction. `<Space>` is used for one thing that has no better key: expand/collapse in a
  tree.
* **Alt chords for panes (`A-1`, `A-2`).** Rejected on measurement: they arrive as `ESC` plus
  a character, so they are indistinguishable from `Esc` followed by that character (§8.1) —
  exactly the collision `Esc` (drill out) cannot afford.
* **A hand-written degradation table per view.** Rejected: the ladder is shared by nine views
  and one renderer, so the per-view order is a *derivation*, and deriving it once in
  `render.ladder_boundary()` means the ADR cannot drift from the layout engine.
* **Three panes per view at 80 columns.** Rejected on arithmetic: three panes plus borders
  leave ~24 columns each, and a 24-column diff is not readable. The third region exists, as
  a strip line inside a pane, and `D3` removes it first.
* **Deferring this ADR until the screens exist.** Rejected: it is a `decision` type for
  `e0.6` precisely because eleven screen tickets depend on it, and `e1.6`'s AC already cites
  "matches the ADR-006 keymap".

## 13. Consequences

1. **`e1.5` inherits a specification, not a suggestion.** The shell implements `MODES`,
   `PRECEDENCE`, `DEFAULTS`, `fit()` and `draw()`'s contract — same names, same precedence,
   same refusal panel. Anything else is a drift bug, and the drift is visible because the
   help overlay is generated from the same table.
2. **Every screen ticket now has a size contract.** `e1.6`'s virtualised rail, `e1.7`'s chunked
   reads and `e3.4`'s aggregation thresholds now have a *documented* size they must be legible
   at, which is what makes their performance criteria meaningful rather than decorative.
3. **The palette's completeness is now checkable**, and a new action that is neither bound nor
   palette-listed fails CI (`K1`). This is a new, permanent tax on every UI ticket and it is
   the price of "everything reachable from the keyboard".
4. **`e5.4`'s freedom is narrower than it may have expected**: the reserved key set in §7.2
   K4 and the reserved chords in §8.2 are checks, and vim fidelity is explicitly off the
   table. Its remaining freedom — override ergonomics, the hint line, which-key affordances —
   is where its value actually is.
5. **Ambient gets built early.** Because the fallback shape of every view is ambient's shape,
   `e1.5` implements the ambient renderer before the queue, which is a small reordering of
   `e5.1`'s work and the reason `e5.1` can depend on `e1.9` and `e4.5` instead of on the whole
   of epic 5.
6. **A new failure class is now visible.** "A pane shows a number it cannot cite" and "a
   degraded frame dropped something silently" are both defects with named owners (`e2.11` and
   the degrading view respectively) rather than user complaints with nowhere to land.
7. **The docs site (`e7.5`) gets its cheatsheet for free**, generated from the same table as
   the help overlay — which is the third time in this ADR that "generate it, or it lies".
