## 0. Why this document exists, and what it decides

Screens get built before anyone decides what they are, and the cost is paid by the user in
the only currency they have: the eleven keystrokes it takes to answer a question they should
have been able to answer with two. `e1.5`, `e1.6`, `e1.7`, `e4.5`, `e5.1`…`e5.6` are all
*screen* tickets, and eleven screen tickets with no shared contract produce eleven
applications: eleven motion models, eleven ways of shrinking, one key bound five times, and
"press `?`" shipping a help overlay that describes a keymap nobody implemented.

This ADR decides five things, and each is checkable rather than aspirational:

| # | Decision | Where | Checked by |
|---|---|---|---|
| 1 | **Nine views**, each with a pane layout, a focus ring and named drill edges | §4, §5 | `test_every_view_has_a_layout_focus_ring_and_drills` |
| 2 | A **sizing contract**: every view is complete at 80×24, and `min`/`floor`/`refuse` are arithmetic, not opinion | §3 | `test_every_view_is_complete_at_80x24` |
| 3 | **One degradation ladder**, applied in one order, announced on screen when it fires | §6 | `test_degradation_is_an_ordered_ladder_not_a_vibe` |
| 4 | **One keymap** with a mode model, a rule against view modes stealing navigation keys, and a chord list the terminal cannot deliver | §7, §8 | `test_default_keymap_is_conflict_free`, `test_no_mode_shadows_the_globally_reserved_keys` |
| 5 | **Three canonical tasks** whose exact keystrokes are published and resolved through the real keymap | §9 | `test_canonical_task_sequences_resolve_as_published` |

The generated tables in this document are rendered from `src/recommender/tui/`
(`python3 -m recommender.tui doc --check` fails CI on drift, like `e0.8`'s config reference
and ADR-004's storage tables). The reason is not tidiness: §7's table is the *source* of the
help overlay (`e1.5`), the palette labels (`e5.4`) and the docs cheatsheet (`e7.5`), and
three hand-copied copies of a keymap is three chances for the help overlay to lie.

## 1. The frame model

```
┌ tab bar ── pinned views; `J`/`K` cycle, `<C-w>1..9` jump, `T` pins this view ── chrome
│ the one live view, which owns every remaining row
├ status line ── epoch · counts · the degradation notice · chrome (never dropped)
└ hint line ── the next likely actions, `e5.4`; chrome, dropped first
```

| Noun | Meaning | Never means |
|---|---|---|
| **frame** | The whole terminal: chrome rows plus exactly one live view. | A pane; a browser frame |
| **chrome** | The frame's non-content rows: tab bar, status line, hint line. | The header of a pane |
| **view** | A full-frame way of answering one question. Nine of them (§4). | A pane, a widget, a screen of a multi-screen app |
| **pane** | A bordered region inside a view with its own focus position and its own data. | A view; a tab |
| **focus ring** | The ordered list of a view's panes. `<Tab>`/`<C-w>l` walk it, pane 1 is where focus lands on entry. | Tab order of a web form |
| **drill stack** | The push-down history of (view, pane, selection). `<Enter>` pushes, `<Esc>` pops one, `<C-o>` walks the whole history back. | Browser history; a back button that forgets the model |
| **overlay** | A floating view (`/` search, `,` palette, `?` help, `-` reason chooser) that borrows the frame and leaves the view behind it untouched. | A new view; a modal that destroys context |
| **mode** | The keymap layer that is live (§7.1). Exactly one interaction mode and one view mode, over `global`; `prompt` and `pick` are exclusive. | Vim's insert/normal split, which this deliberately does not copy |
| **tab** | A pinned (view, scope, filters, selection) tuple. `T` pins, `J`/`K` cycle, `<C-w>c` closes. Tabs are *contexts*, not documents. | A file buffer; a terminal tab |
| **scope** | The episode or episode range every view in the frame is currently answering about. `m` marks an endpoint, `c` compares with it (`e5.3`). | The current directory |

Three structural rules:

**R1 — one live view, no split views.** The frame holds exactly one view. Two views side by
side at 80 columns is two unreadable views; the way to see two things at once is to change
the *scope* (`c` for compare, `e5.3`), not the frame. The one exception is inside a view:
the diff's split/unified toggle (`\`) splits a *pane*, and it is opt-in and needs ~100
columns, below which it degrades back to unified (§6.3).

**R2 — focus is lateral, drill is vertical.** `Tab`/`<C-w>h`/`<C-w>l` move focus between
panes without changing the scope; `<Enter>` pushes a drill, which changes what the scope
*is*. This is the distinction that makes `Esc` predictable: `<Esc>` pops exactly one push,
and it never quits the application. The only quit chord is `<C-c>` (§8.1).

**R3 — every pane's content is ordered by decreasing importance.** The layout engine drops
content from the end of a pane when the terminal shrinks (§6). A pane whose most important
fact is at the bottom loses that fact first, which is why the ordering rule is a contract on
`e1.6`/`e1.7`/`e2.10` and not a rendering detail. The test suite enforces that no mock line
exceeds its pane's documented width, so a layout in this document cannot be a wish.

### 1.1 Modes, precedence, and why `prompt` wins outright

<!-- BEGIN GENERATED: modes -->
| Mode | Kind | Exclusive | Live when |
|---|---|---|---|
| `prompt` | interaction | yes | A one-line text field owns the keyboard (search query, palette filter, reason text, path). Everything typed is text. |
| `pick` | interaction | yes | A single-key chooser is open (dismiss reason, snooze window, format). One keystroke chooses; there is no text entry. |
| `list` | interaction | no | A list pane has focus: episode rail, file tree, dependency table, search results, treemap rows. |
| `body` | interaction | no | A content surface has focus: hunk view, episode card, graph canvas, artefact preview. |
| `timeline` | view | no | The timeline (episode rail + card) is the live view. |
| `diff` | view | no | The diff view is the live view. |
| `structure` | view | no | The structure treemap view is the live view. |
| `graph` | view | no | The module graph view is the live view. |
| `deps` | view | no | The dependency view is the live view. |
| `artefact` | view | no | The export-preview view is the live view. |
| `ambient` | view | no | Ambient mode is the live display mode. |
| `global` | root | no | Live whenever a non-exclusive mode is not holding the key. Owns view switching, overlays, review actions and the frame. |
<!-- END GENERATED: modes -->

`prompt` and `pick` are **exclusive**: while a text field or a chooser owns the keyboard,
`global` does not fire. Without this, typing `graph` into the search box would visit three
views (`g`, `p`, `a`). The cost is that `<C-w>` (delete-word in readline) is not the focus prefix inside a
prompt, so `prompt` binds it to `prompt.delete_word` and the frame prefix is unavailable
there — the price of being able to type the letter `w`.

Precedence is `prompt → pick → list → body → <view> → global`, first binder wins. A view
mode may add keys; it may not steal the navigation keys (§7.2 K4).

**One motion, wherever it lands.** The list-motion actions (`list.down` … `list.last`) have exactly
one implementation — `motion_target` in `fathom-tui/src/app.rs` computes the target row from the list's
own geometry — and it is shared by every pane that shows rows, by both boxes' result lists, and by the
comparison panel (§5.3). "Middle of what is on screen" is therefore the same arithmetic in a worklist, a
palette of 60 actions and a 400-line diff; `crates/fathom-tui/tests/motion_parity.rs` fails when a
surface drifts from it, and `every_view_resolves_the_motion_chords_to_the_same_actions` fails when a
view rebinds one chord to something else. What exclusivity forces is only the *reaching*: in `prompt`
the letters type, so the box walks with `<C-n>`/`<C-p>`, `<Tab>` and the arrows (§5.8, §7.5).

## 3. The sizing contract

Four numbers per view, three of them derived:

| Name | Meaning | How it is produced |
|---|---|---|
All four are **frame** sizes — chrome included — so that a reviewer can measure them
against a real terminal with `stty size` and get the same answer the table gives.

| Name | Meaning | How it is produced |
|---|---|---|
| **ideal** | The documented size this ADR draws the layout at. Chosen so it is ≤ 80×24, because the layouts in §5 must be readable on the machine the reviewer is already SSH'd into. | Declared per view in `views.py`; `test_drawn_layouts_fit_their_documented_size` proves the drawing matches |
| **min** | The smallest size at which the *documented pane set* still renders, every pane at its documented minimum width. | `Σ pane.min_cols + gutters + frame`, derived in `render.min_cols_view`; rows declared as `min_rows` |
| **floor** | The smallest size the documented pane set can be squeezed to, i.e. after the whole ladder has fired and before any pane is dropped. | `min − Σ ladder recovery`, clamped at the single-pane floor (`render.floor_cols`) |
| **refuse below** | Below this the view is not drawn at all: the refusal panel replaces it (§6.6). | Columns: the primary pane's `hard_min`, taken **without** its frame, because the frame is sold two steps earlier. Rows: the chrome left standing after the ladder (the status line, one row) plus the view's own content floor |

Read three things off that table:

1. **Every view is complete at 80×24.** The `min` column is below 80×24 everywhere, and the
   layouts in §5 are drawn at the ideal size. `e5.5`'s matrix (80×24, 100×30, 120×40,
   160×50, ultrawide, 40×10) is asserted in §6.5.
2. **Ambient has the smallest floor**, and it is the only view whose floor is stated in
   ADR-001 rather than derived here: §4.1 promises ambient fits a 40×3 tmux pane, so ambient
   declares a 40-column line budget and two content rows (§5.7), and `refuse_below` reads
   40×3. That is the promise paid for rather than restated. ADR-001 §4.1 also says ambient
   fits 80×12, which the table shows with room to spare.
   narrow tmux pane (`e5.1`'s AC) is not an edge case.
3. **`min` is derived.** Nobody can quietly widen a pane and leave the documented minimum
   lying, because the number is arithmetic over the pane table.

Growth above ideal is a rule too, because "it just stretches" is not one: spare columns go
to the primary pane first until it is twice the width of the widest secondary, then split
evenly; spare rows go to the primary pane's content; pane strips never grow. This is what
keeps a 240×60 terminal looking like a considered design instead of a blown-up 80×24.

## 5. The eight views

### 5.1 Queue — `q` · **deleted**: §5.1.2 is what replaced it, and §5.1.1 still binds

*What is the next thing I have to look at, and why that one?* Owned by `reco-wsj` (`e4.5`),
rendered from the store's ranking query (`e4.4`) and dispositioned into the ledger (`e4.6`).

> **`e10.1` (`reco-ydek.1`) decided it; `e10.3` (`reco-ydek.3`) deleted it.** There is no layout
> block here because there is no pane: §5.1.2 is the decision, and it names the Timeline (§5.2) as
> home, puts the four acts on the rail, and puts the retrospective in the same pane. The worklist,
> its `order: risk × staleness × blast radius` strip and the `queue-1` ordering are gone, and so is
> `q` — retired to §8.2's reserved set rather than handed to whatever wanted a spare key. What
> survives in this section is §5.1.1, the episode card's band list: the queue hosted it, never
> owned it, and every card on screen still implements it.

Three rules out of the deleted pane's notes survive, in §5.2's hands now. They are named here
because pages cite them by this section number:

* **A list names the order it is in, in words the renderer implements.** That was the worklist
  strip's job and it is the rail strip's job now — `order: newest first`, with the parts and their
  priority in §5.1.2 §3. An unnamed order is the thing that made the old strip necessary.
* **`w` prints the same feature vector `fathom why` prints.** The *place in a ranking* left with
  the ranking; the arithmetic did not (§5.1.2 §5).
* **The acts are single-keystroke from the list pane** — `x`, `f`, `-`, `z` act on the rail's row
  without drilling — because `e4.5`'s bar, a hundred episodes cleared in under five minutes, did
  not get easier when the pane went.

#### 5.1.1 The episode surface — one pane, five bands, and what `w`, `i` and the card focus mean

*Decided by `reco-5js3.1` (`e9.1`). Executed by `reco-5js3.2` (`e9.2`) and `reco-5js3.3`
(`e9.3`): this is the page they implement, and a row that is not on it does not get built.*

The card and the two modes that replaced it had grown into each other. The card printed what
changed, where it landed, what the episode touches and what needs attention; `w` replaced it
with the episode identity, the vector, every reason and the whole ceiling; `i` replaced it
with the intent, its plan and its declared scope. A reviewer pressed `w`, found half of what
they wanted, pressed the other key, and found the other half phrased differently. Nothing on
paper said where one surface stopped, so each surface stopped where its own author stopped.

The duplication was not only *between* the three surfaces. It was inside the card, which printed
four of the same episode's figures nine times inside one pane — eleven across the two panes of
one frame — in three vocabularies:

| the figure | the card prints | and also | and also |
|---|---|---|---|
| the churn | `size +412 −90 · 12 files · 1 binary` — the spine's columns, reformatted in the pane | `x what +412 −90 · +3 more` — `insight::brief()`'s `what` row, whose first figure is the same `+412 −90` | the worklist row's own `+412 −90` |
| where it landed | `where src/store (7) · src/core (3)` — `card::top_paths`, a count of files per two-level prefix, computed **in the pane** | `x where crates/fathom-tui/src 12f +412 −90 · src/store 7f +58 −12` — the document's rollup, by full parent directory and ranked by churn | *(nothing: the two answers can disagree)* |
| the ranking | `risk spine-1 62 · rank 4 of 7` | `vector spine-1 62 = surfaces 50 + author 8 + size 4` | `x attention spine-1 62 = … · rank 4 of 7` — the document's row, which is `RiskView::headline()` with the place appended when there is one, i.e. **the same string twice** |
| the ceiling | `blind` a spine cannot see 7 things — `w` lists them all (`blind_spot_note()`) | `blind` a spine cannot see: `<first>` (6 more) — `w` lists all 7 (`push_risk`'s own wording) | the `w` pane's seven bullet rows |

The `where` row is the worst of the four, because `card::top_paths` counts files per
two-level path prefix and the document rolls full parent directories up by churn: the pane and
the document can print **different answers to the same question** two rows apart, which is
ADR-001 §7.10's "a surface computing its own truth is a bug" with a screenshot. `w` and `i`
were then built on top of that — a key that trades a pane duplicating its own numbers for a
pane duplicating the card's.

**The one question.** One pane answers one question, and the pane is the `card` pane of `q`
and `t` — the only place in the shell whose whole subject is one episode:

> **What did this episode do, and what should I open first?**

Every row in it must earn its place by being part of the answer to that sentence. That is the
test, and it is what the retired pane failed: the *plan* is part of "what did it do" only
indirectly, the *declared scope* is evidence for a finding rather than a finding, and the
member SHAs, the boundary rule and the session/turn pair are facts about **the record** —
how the tool came to know this episode — which no reviewer opens the card for.

The rail, the worklist row and ambient's glance line are not episode surfaces: they print
figures the model owns in fewer columns, and §5.1.1 governs the summarising pane only.

**Five bands, one order, and who renders each string.** A *band* is a section of the episode
pane; a band prints one row per figure, at most, and every row's string comes from the
function named in the last column. The order is a rule, not a preference: it is
`SectionId::ALL`'s order, the delta document's reading order, which `verify` already pins for
the document — so the card, `fathom analyze`, the export and an agent's tool result read a
reviewer's question in one sequence.

| # | band | the question a reviewer can say out loud | rows it prints, in order | who renders every one of those strings |
|---|---|---|---|---|
| 1 | `what` | "what changed, and how much of it is real?" | one row | `brief()`'s `what` row when a delta document is in hand — churn first, then files, then the noise fold and the counted remainder; the spine's own `n_add`/`n_del`/`n_files` columns when no document was handed over, which is the only case in which the pane may format a number itself, from cited columns. `e8.6`'s complexity row lands **in this band** and nowhere else |
| 2 | `where` | "where did it land, and did the tree move?" | one row | `brief()`'s `where` row: `e2.3`'s shape sentence when supplied, then the churn-ranked directory rollup, with its counted remainder. `card::top_paths` is deleted with the second row it existed to feed |
| 3 | `reach` | "what does it touch, and what could it break?" | four rows, in the document's order: `dependencies`, `surface`, `tests`, `blast` | the four `brief()` rows — a dependency that can now be reached, an operator-action surface and what it asks for, tests moved with the code or not, and the reach with its basis and its confidence |
| 4 | `rank` | "why is this one in front of me?" | brief: one row (the vector, with its place) + the surfaces badge + the counted ceiling. Expanded by `w`: every reason line, then every blind spot, then the ceiling line | `brief()`'s `attention` row (the document's own spelling of `RiskView::headline()` plus the place), `RiskView::badge()`, `RiskView::reasons()`, `RiskView::blind_spot_note()`, and `BLIND_SPOTS`' own lines |
| 5 | `intent` | "what did the agent say it was doing?" | **one line**, in three states | `delta.episode.intent` — the text with `via <source> · <confidence>`, or `no text captured · prompt <sha> · via <source>`, or the named absence and its reason. When there is a plan or a declared scope behind it, the line ends by naming the verb that prints them |

Four rules about that list, all four of them checkable:

1. **One row per figure, and no figure twice.** A row belongs to exactly one band; a band
   prints each of its figures once. Two rows labelled `blind`, or a `vector` row beside an
   `attention` row carrying the same bytes, is a defect in this pane, not a design choice.
2. **The pane authors no prose about a figure.** Every string is `brief()`'s, a `RiskView`
   accessor's, `insight::intent_block()`'s, or a cited spine column. The one pane-authored line
   that was in the expanded ranking band — *"read those by hand: the ranking is a reading
   order, not an all-clear"* — moved into `fathom-analyze` as `risk::CEILING_NOTE`, reached
   through `RiskView::ceiling_note()` beside the `blind_spot_note()` it belongs to (`e9.3`), so
   the ceiling is the model's words in the model's voice and the pane only places them.
3. **No band is optional and no band is added without amending this table.** A missing
   analysis prints its own gap, reason and fill verb (`e2.10`'s rule, `e5.9`'s copy); a new
   figure gets a delta-document field before it gets a row. Complexity, when `e8.6` lands it,
   is band 1's fourth figure, not a sixth band.
4. **The row budget spends the bands first.** The budget is the rows the frame hands the `card`
   pane, and the renderer's own plan is the only place that counts them: **eighteen at the 80×24
   both panes above draw** — the pane's title row and its footer strip are chrome, and the card
   gets neither — twenty-four at 120×30, ten at the timeline's 61×16 minimum, seven at its 41×9
   ladder floor. `the_budget_is_the_rows_the_frame_gives_the_card_pane` in `tests/episode_card.rs`
   pins those four against `frame_plan` rather than off a layout mock, because a budget nobody
   checks is a rumour and this page had already written nineteen where the plan says eighteen.
   The header takes two — `e8f1a2 — <summary>`, and the
   facts row `4 commits · 0:12 ago · ⚑ unread` — plus one for every warning
   that says the row cannot be trusted at all (ADR-003 §6.3's `gone —`, a failed
   `integrity` self-check). The five bands come next, in order, and **no band is cut to make
   room for a provenance row**: `members`, `boundary`, `session` and the benign model stamp
   print afterwards, in that fixed order, and only if every band fit. Warnings are never
   demoted; provenance always is.

When the bands and the header do not fit, the pane sells rows before it hides any: **every figure
takes exactly one row**, cut at the row's end, and what the cut keeps is the counted remainder the
document wrote itself (`· +3 more`) rather than a `…` invented in the pane. Only then do rows fall,
provenance first and per rule 4 — and what fell is named, not lost: the last visible row counts it
and says which key brings it back. That is `e9.2`'s half of the bargain, and it is what makes the
modes in this pane unnecessary: a pane whose tail is unreachable needs a key to swap its content,
and a pane with every band on the screen does not.

The **window** is the other half, and `e9.3` paid it: `w` folds the ranking into this pane as band 4
and `i` does not survive, so the card is a document rather than a glance — and a document you cannot
move inside is the thing rule 4 was written to avoid. The `card` pane therefore reads
`App::scroll_of` like every other secondary pane, walked by the one shared motion (§1): `j`/`k`,
`H M L`, `gg`/`G`, `<C-d>`/`<C-u>` and the wheel. Its overflow row names that motion — … 21 more
rows — `j` walks them, `G` walks to the end — with a short form for the twelve-column card the
ladder leaves at the floor, because a counted remainder clipped to `… 21 more r…` is the silent cut
wearing the honesty badge. Before `e9.3` that row could only point at `<C-w>o`, because the pane
owned no scroll offset, and a scroll a pane cannot show is a key that lies: which is why the motion
arrived with the content that needed walking and not before it. `<Esc>` has no mode left to pop
here; it pops the drill.

**What the pane does not answer, and where the deep form lives.** A 29-column pane is a glance;
a document is a document, and it has a verb.

| the deep form | lives in | what the pane prints instead |
|---|---|---|
| the per-feature table — every feature, its weight, its contribution, `9 of 12 features measured · weight denominator 0.76`, the `τ` comparison, each unmeasurable feature with the ticket that owns it, `--weight` and `--calibrate` | `fathom why` (`risk::score::render`), which is the model's own renderer and not the CLI's | band 4, brief: the vector, its place, the badge, the counted ceiling |
| the intent document in full — the request text, its source and confidence, the plan items, the declared scope, the prompt digest | `fathom show <episode>`, through `insight::intent_block()` — the same function the delta document renders through | band 5's one line, in its three states, naming `fathom show` when there is a plan or a scope behind it |
| every figure with its evidence pointer, per section | `fathom figures` / `fathom analyze --json` | the same first figure, no pointers — the pane is a summary, and the worklist row's `✱` is where a figure is a finding |

Two things follow, and they are what keeps the CLI verb from being a duplicate of the pane and
the pane from being a duplicate of the CLI:

* **`fathom why` keeps the arithmetic a pane has no columns for** — the feature table, the
  denominator, the `τ` comparison, the config notices and the weight overrides. None of it is
  ever drawn in the shell, and no band grows to hold any of it.
* **the pane keeps the one fact `fathom why` cannot have**: `rank N of M` for *the set on
  screen*. `RiskView::rank`/`ranked` are the caller's, because a place in a set is not a fact
  about one episode — the CLI scores one episode and is silent about the queue, and the pane
  knows the queue.

Neither surface gets **a second narrative**. The reasons on the card are `RiskView::reasons()`
and nothing else; `fathom why` prints `risk::score::render()`; both are model-owned, and no
surface paraphrases a figure because a paraphrase is a second figure wearing the first one's
clothes.

**The `i` pane does not survive.** `intent.show` is deleted, and intent becomes band 5's one
line.

* It was the duplicate. Everything the `i` pane printed except two lines is what the card's
  intent row already printed, in the same words from the same `intent_block()` — so what it
  added over the line was the plan items and the declared scope, and both are facts about the
  *brief*, not about the change.
* Those two are *evidence for a finding the card already prints*. The scope-creep finding
  (`e4.3`) names the path that was touched without being declared; the declared list is what
  the claim was measured against, which is evidence, and evidence has exactly one home per
  ADR-001 §7.10: the delta document, printed whole by `fathom show` and shipped in
  `fathom analyze --json`.
* The keystroke mostly shows an absence. Hooks v1 carries a prompt *digest*, and a digest is
  what this project's own streams carry
  ([verification](../harness/verification.md) §1), so for most rows `i` printed
  `no text captured · prompt <sha>`. A key that trains the reviewer to press it and shrug is a
  key spent for a shrug.
* What it justified stays: **the rule that an absence has to be drawn** (`e4.2`'s rule, and the
  only rule of that pane worth keeping) moves to the one line, which must keep distinguishing
  *not on this row* / *no text captured* / *no recorded intent, because* `<reason>`. The
  assertions in `crates/fathom-tui/tests/intent_card.rs` move with it — same three states,
  same frame, now asserted on a row instead of a mode.
* And when the line has something behind it, it says where: the line names `fathom show`
  rather than a keystroke, because a retired key must point at where its answer went.

The honest counter-case: a reviewer who checks a change against its declared scope in the
shell will miss `i`. If that turns out to be real, the shape is a **drill**, not a mode —
§4's own doctrine is that a pane which cannot be tied to its view's question should be a drill
— and it needs an amendment here naming the question band 5 cannot answer. It does not get
rebound quietly. `i` goes to §8.2's reserved-for-user set, which is the mechanism that keeps a
retired letter from being silently reused by whoever wants a free key next.

**`w` survives, as an expander.** `w` stops swapping the pane and starts growing one band, in
place, with every other band still on screen. Three reasons it keeps its key while `i` loses
its:

1. The model already promised it. `RiskView::blind_spot_note()` prints *"a spine cannot see 7
   things — `w` lists them all"*, and that string ships in the delta document, the card and
   the plain frame. Either `w` really lists them all, or the shipped string gets edited to fit
   a key — which is putting the cart where the harness goes.
2. The ceiling cannot be cut, so *something* in the pane must be able to print the whole list,
   or the pane sends the reviewer out of the pane for a fact that decides whether they trust
   the number. `w` is where they already are.
3. The rest of the docs teach `w` as "interrogate that number": the queue strip's own
   *order: risk × staleness × blast radius (`w`)*,
   [the risk page](../concepts/risk.md) and [the timeline](../concepts/timeline.md), both of which say a
   ranked row is interrogable with `w`. None of them becomes a lie; only the word *pane* does. `i` had no such web — it had a
   pane and a card row.

Expanded, band 4 prints the model's own rows and nothing else: every line of
`RiskView::reasons()`, then every line of `BLIND_SPOTS`, then the ceiling note, then the
model's *reading order, not an all-clear* line. It does not print the feature table; that is
`fathom why`'s, and the expanded band ends by saying so when it has reason to.

**What each key means afterwards.** Keys are a published contract (§7.0's K1, §7.3, §7.4, the
generated cheatsheet), so this is the whole of the change, with the ticket that has to make
the tables say it:

| key | today | after `e9.3` | what happens to the old action |
|---|---|---|---|
| `w` | swaps the card pane for the ranking pane; `w` again or `<Esc>` goes back | **bound in `global`, unchanged binding.** Toggles band 4 between its brief rows and its full rows, **in place**; every other band stays on screen; `<Esc>` has nothing to pop here | `risk.explain` keeps its id, its binding and its hint-line seat (§7.5's eight-item budget); the label becomes `Why this rank: every reason and the whole ceiling`, and the registry regenerates §7.3, §7.4, the palette, the hint line, the cheatsheet and §9's T1 note from that one change |
| `i` | swaps the card pane for the intent pane | **unbound** | `intent.show` is deleted, not unbound, so it leaves the registry, the palette, the help overlay and the cheatsheet with it — and K1 is untouched, because there is no action left to bind. `i` joins §8.2's reserved-for-user set: the default build binds nothing, a user may bind it, §7.6 says what it would take to bind it in the default table again |
| card focus | a document you could not move inside: the pane truncated its own tail and pointed at a mode to see the rest | a windowed document: `j`/`k` `H M L` `gg` `G` `<C-d>` `<C-u>` and the wheel walk it with the one shared motion (§1), `<C-w>o` still gives it the frame, `<Enter>` still drills to `d`, `<Esc>` pops the **drill**, not a mode | `e9.2`'s half came first: one row per figure, provenance last, and the row that falls counts itself and names the motion that walks it, so no band is reachable only through a mode. `e9.3` paid for the window: the card took sections, became a document, and reads `App::scroll_of` like every other secondary pane |

And what disappears with the modes, by name, so `e9.3` can be checked off against it:
`App::explain`, `App::intent`, `App::explaining`, `App::showing_intent`; the three-way branch
in `App::queue_body` and `App::timeline_body`; `timeline::risk_lines` and
`timeline::intent_lines` (folded into the band renderers in `timeline::card`); `card::top_paths`;
the pane's own `size`, `risk`, `vector` and `blind` rows; the toast *"… the card pane explains
it; `w` again to go back"* and the overflow line *"… `i` again, or `<Esc>`, to go back"*;
`<Esc>`'s mode-clearing arm and its toast; and the intent line's *"`i` for the plan and
scope"* tail, which must stop promising a keystroke that no longer exists.

**The rule that keeps this from coming back: one figure, one string, one surface.** ADR-001
§7.10 says a surface computing its own truth is a bug; §5.1's binding note already applies it
by name to one figure ("`w` must print the same feature vector `fathom why` prints"). Here is
the general form, and it is what a reviewer of a TUI ticket checks:

1. Every figure has **one rendering function**, in the crate that owns the figure. A pane may
   place it, wrap it and truncate it with a counted remainder; it may not re-word it.
2. Every figure has **one episode surface**. The card is the only episode surface, so a figure
   the card prints may not appear in another pane *in other words*, and may not appear twice in
   the card in two spellings.
3. Where two surfaces must show the same figure — the strip, the rail row, the card, the
   `--plain` frame, the CLI — they show **the same bytes from the same accessor**. Identical
   repetition across surfaces is allowed and expected; paraphrase is the failure.
4. A PR that adds a row to an episode surface names, in the description, **the band it belongs
   to and the function that renders its string**. If the answer is "no function, it formats it
   here", the figure gets a delta-document field first. That is the review gate, and it is two
   questions a reviewer can ask without opening the render code: *which band, and who renders
   it?*

Three checks, named so the children owe them rather than inventing them:

* `crates/fathom-tui/tests/episode_card.rs` (`e9.2`, `e9.3`) — the published list, read
  **out of this file** the way `tests/layout.rs` reads the ladder tables, then held against a
  real frame at 80×24 with a fully populated delta: `the_card_prints_the_adrs_bands_in_order`
  (labels, in order, each at most once); `expanding_band_4_keeps_every_other_band` (the pane
  grew, it did not swap); `no_key_swaps_the_card_pane` (every view × pane combination pressed
  with `i` renders byte-identically, and `i` is in no mode's table); `one_figure_one_string`
  (each figure string the model produced appears at most once in the pane body, and the
  vector row is `RiskView::vector`'s bytes).
* `crates/fathom-cli/tests/risk_rank.rs` (`e9.3`) — `the_cli_and_the_pane_print_one_vector`:
  the CLI's line for a planted episode contains the card's ranking row verbatim, which is
  §5.1's binding note restated for the surviving surface instead of the retired one.
* `tools/check_docs.py` (`e9.3`) — a `retired surfaces` rule: the tokens that named the
  retired panes as live (*the `i` pane*, the *`w` pane*, `intent.show`, `intent_lines`,
  `risk_lines`, "`i` for the plan") may not appear in `README.md` or under
  `docs/concepts/`, `docs/reference/`, `docs/recipes/`, `docs/harness/`. It uses the same
  globs and the same `transcript` marker escape as `tools/check_ticket_claims.py`, so a page
  quoting an old printout is allowed to quote it, and `docs/adr/` stays dated-and-exempt for
  the reason `check_ticket_claims.py` gives.

**What on this page is generated, and what is not.** The tables above are hand-written prose,
and now normative: `episode_card.rs` parses them out of this file, so a band added here with no
renderer, or a renderer that drifts from here, fails CI. Everything else on §5 — the ASCII
layouts, the pane tables, §7's keymap, registry, palette, hint line and §9's tasks — stays
generated, and still draws **today's** build: the layouts above them keep the `w`/`i` mode
until `e9.3` deletes the modes and `python3 -m recommender.tui doc` re-renders them. That is
the rule this ADR has had since `e0.6` — the page and the code move together, and `doc --check`
says when they have not — so the honest sequence is: this page decides, `e9.2` and `e9.3`
build, the generated blocks follow in the same commits, and `doc --check` guards the join.

#### 5.1.2 The retirement — what is home, where the acts and the audit trail live, and what the label was load-bearing for

*Decided by `reco-ydek.1` (`e10.1`). Executed by `reco-ydek.2` (`e10.2`, the acts onto the rail),
`reco-ydek.3` (`e10.3`, the deletion), `reco-ydek.4` (`e10.4`, the label) and `reco-ydek.5`
(`e10.5`, the vector). This is the page they implement; a thing not decided here is not theirs to
invent. Like §5.1.1's closing paragraph says of the generated blocks, everything decided here is
prospective until its ticket lands — the layouts, the inventory, the keymap and §9 keep drawing
this build, and `doc --check` guards the join. Two strings written elsewhere are superseded by
name here, and item 8 below names them.*

**Why two features go in one epic.** They are not one feature; they are one mistake, made twice.
Each put a computed guess in front of the reviewer as a fact about the row, and each cost a place to
be. [the ranking half of the risk page](../concepts/risk.md) asked *which should a human read first*; the
ranking answered it and the reviewer answered it by opening the timeline, and the answer in use is
the second one — a ranked list of the same episodes the rail already shows is one question asked
twice, not a second insight. Attribution was answered as a word on every row, when for a large
slice of rows the honest word is *nobody claimed this*: the ladder in
`fathom-ingest/src/attribute.rs` reaches rung 8 (`identity`, confidence 0.50) — "a real identity and
no agent evidence at all" — which is exactly the state an agent session with no recorded harness
arc lands in. The badge is therefore confidently wrong in the cases a reviewer cares about, and an
inaccurate label is not neutral space: it teaches the reviewer to distrust the row. **Retire the
ordering and the word; keep the acts, the ledger, the counts and the datum.**

The rule the two retirements add up to, and the one a later ticket gets checked against:

> **A datum a human is never shown may not decide what that human sees** — may not score it, sort
> it, filter it or bucket it. Either print the datum with its confidence and its evidence, or do not
> let it steer the screen.

That is `e10.5`'s argument about the risk component, generalised, and it cuts both ways: a label
that stops being printed may not quietly go on scoring the episode, and a label that stops being
printed may not quietly survive as a filter.

**1. Which view is home, and what opens on start.**

| | today (drawn in §5.1) | after `e10.3` |
|---|---|---|
| home view | Queue (`q`) | **Timeline (`t`)** |
| what `fathom tui` opens on | the queue, worklist focused | **the timeline, rail focused (pane 1), no filter applied** |
| frame-owning views | eight, plus `/` (§4) | **seven**, and §4's inventory regenerates to say so |
| K3's globally reserved letters | `q t d s g p a o` + `/` `,` `?` | **`t d s g p a o`** + `/` `,` `?` |
| `q` | `view.queue` | **retired** — see §7.6 |

Four things follow, none of them obvious from "make the timeline home":

* **`t` stays the home letter.** Moving home onto the freed `q` would make the key for the thing the
  reviewer reads change because a pane they never used went away. The letter belongs to the view.
* **Home is not a filtered view.** No default `state=unread` is introduced: hiding two thirds of the
  rail behind a strip line is §10.3's partial-state machinery doing the work of a filter, and
  ADR-001 §7.2 does not care that the hiding was the default. The strip's unread count (§3 below)
  is the "what is left" signal, and `F` is the reviewer's own choice to narrow.
* **`q` is retired, not free.** `view.queue` leaves the registry — which takes its palette row, its
  help-overlay line and its cheatsheet row with it, per §7.6's first rule — and `q` joins §8.2's
  reserved-for-user set. It is the user's letter, not `e10.3`'s to hand to whatever wants a spare
  key; §11 carries the bar for binding it in the default table again. This is §7.6's second
  instance and its first where a whole view is the thing deleted.
* **Session state keeps its promise.** `e1.11`'s `tui.tabs` rows are `view:title`. A stored tab
  naming a view this build no longer has is decoded under session-state §1's existing rule —
  *applied, newer than this build, or damaged*, every failure adding a warning and continuing — and
  it applies as **the home view, with a warning that names the view it replaced and the filter and
  selection it carried** (both of which the timeline can carry). A tab that silently vanished in an
  upgrade is a reviewer losing their afternoon to a version bump, and "we deleted a view" is not a
  reason to lose a cursor. `a` (ambient) is untouched: it is a display mode over the same model,
  ADR-001 §4.1's "one keypress drills in" survives, and its drill now lands on the rail because
  that is where the episode gets selected.

**2. Where the four acts live, and which key owns each.**

| act | key | mode | what it acts on | what changes in the same frame |
|---|---|---|---|---|
| accept | `x` | `global` (unchanged) | the frame's selected episode: the rail's cursor row, or the card's episode when the card has focus | row glyph `⚑`→`✔`; the strip's unread count drops by one |
| flag | `f` | `global`, then `prompt` | same; the note is required, as today | `⚐` |
| dismiss | `-` | `global`, then `pick` | same, plus a code from the closed vocabulary (extended by `dismiss_reasons`, item 2's last bullet) | `×`, and the retrospective gains a line |
| snooze | `z` | `global`, then `pick` | same, plus the condition (`7d`, `next-index:N`, `new-in-session`) | `z`, and the strip's snoozed count rises |

* **The keys and the plumbing already ride the rail.** All four are `global` bindings (§7.3) and
  `App::act_target` already resolves to the timeline's selection for every non-queue view, so what
  `e10.2` moves is the *host of the feedback*, not the address of the act. What the queue actually
  contributed was the worklist as target and "the row leaves the list" as feedback, and it is that
  feedback which has to be re-expressed as a glyph and a count.
* **The write comes first and the rule moves whole.** `Ledger::record` is called before any shell
  state changes, a refusal is a toast naming the cause, and `None` (no ledger) keeps acts in memory
  and says so out loud. The module that owns this after `e10.3` is not called a queue, and it owns
  both halves of the rule; `tests/queue_triage.rs`'s `accept_writes_before_it_moves_and_the_row_leaves_the_queue`,
  `a_ledger_that_refuses_keeps_the_row_exactly_where_it_was` and
  `with_no_ledger_an_act_is_honest_about_living_only_in_memory` move with it rather than being
  rewritten green — and `e10.2` moved them literally: they are `tests/timeline_acts.rs`'s now, the
  first renamed to say what a rail has to prove (`accept_writes_before_it_marks_and_the_row_reads_accepted_in_the_same_frame`,
  because nothing leaves a chronology), and `queue_triage.rs` keeps only what the pane owns until
  `e10.3` deletes it. The stamping rule travels in the same crate and is not a new idea — `record_for`
  captures the risk and the model name *at the moment of the act* and never recomputes them.
* **The acts do not advance, and that is a decision, not an oversight.** In the queue `x` advanced,
  because a queue's whole content is undispositioned work. The rail is a chronology and the cursor
  is a place in time: a keystroke that jumps the cursor forward while the reviewer is still reading
  the row they just accepted breaks the next keystroke, which is `d` on *that* episode nine times in
  ten. The reviewer working a run of rows uses the filter that already exists (`F` → `state=unread`)
  and walks with `j`, or uses the published `n` (next match). `clearing_a_hundred_episode_queue_costs_the_shell_seconds_not_minutes`
  is `e4.5`'s five-minute bar as a test; it becomes a timeline test, filter and motion included,
  and it may not be satisfied by a cursor that moves under the reviewer's hands — `e10.2` re-hosted
  it as `clearing_a_hundred_episode_rail_costs_the_shell_seconds_not_minutes`, with the walking done
  by `j` and a filtered rail's departure proved separately
  (`a_filtered_rail_lets_the_row_go_when_the_act_makes_it_not_match`).
* **The glyph is the confirmation.** `e10.2`'s AC — the row reads as accepted in the same frame,
  with no second view to confirm it — is §5.2's row state column doing its job, and the state glyph
  is the one cell the ladder promises never to drop (§5.2, `e5.6`).
* **One config key is load-bearing here, and it is named after the dead view.** `[queue]
  dismiss_reasons` extends the closed vocabulary, which survives; the section name does not describe
  anything that survives. `e10.3` renames it to `[review] dismiss_reasons` and **keeps honouring the
  old key with a notice** naming the new spelling — a rename that silently ignored a repository's own
  vocabulary would be the §7.2 failure (a filter that quietly stopped filtering) wearing a config
  file, and the ordinary `unknown_key` nearest-name warning is not enough for a key that changes
  *behaviour* rather than disappearing. Keys are named where they are documented
  ([config.md](../concepts/config.md)), which is `e10.3`'s page to amend.

**3. What the strip under the rail says.**

The queue's strip reads `order: risk × staleness × blast radius (w)`; the rail's reads
`filter: area=any state=unread (F edits)`. After `e10.3` one strip does both jobs, and §5.1's
binding note — *the strip must name the ranking function* — survives in its general form: **a list
names the order it is in, in words the renderer implements.** Chronology is an order and gets named
as one, because an unnamed order is the thing that made the queue's strip necessary.

| # | part | example | why it sits here |
|---|---|---|---|
| 1 | the order | `order: newest first` | the successor to `order: risk × staleness × blast radius`. The words must be what the rail's sort and `group` actually do: grouped by day (or by session under `group=session`), newest first inside each group, `oldest first` when the reviewer has set it. **No strip may print an order the renderer does not implement** — that is the whole reason this line exists |
| 2 | the open-work count | `7 unread` | what keeps *caught up* falsifiable (§5.7, ADR-001 §4.5). Replaces the queue's `7 open`; it is the same number, because it was always a count of episodes in open review states and never a property of a pane |
| 3 | the filter, when one is live | `filter: state=unread (F edits)` | unchanged text, unchanged `F`, unchanged position of honour: a live filter is a claim about the *set* and the thing most worth undoing |
| 4 | the risk model's name | `risk spine-1` | the row prints a number and the strip says where it came from. Printed **only while the rows print a risk number**: a model name beside no number is a citation to nothing, so below the ladder's `NoRisk` rung it is gone, and it changes in the same commit `e10.5` changes the arithmetic |

The parts are in decreasing priority, which is §1's R3 applied to a footer: at the rail's 42 ideal
columns the strip is `order: newest first · 7 unread · filter: state=unread (F) · risk spine-1`, at
its 32-column minimum `order: newest first · 7 unread (F)`, and the last thing standing is the
order. In the retrospective's state (§4) the strip is replaced wholesale and says so:
`ledger: 41 acts · 12 dismissed · 3 reasons · Dana Stahl`, or the no-ledger sentence,
`no ledger — nothing written this run`.

**4. Where the retrospective lives.**

On the rail, as a second state of the same list pane — the same trick the worklist uses today, and
for the same reason: the question *what did I wave through, and under which excuse* is asked while
dispositioning, one keystroke from the acts that produce the records. `r` keeps the job; the action
is renamed `queue.retrospect` → `review.retrospect` and moves to `global`, which is free of conflict
because `r` was bound only in the dying `queue` mode. From any view, `r` puts the timeline on screen
with the rail listing *acts*; `r` again puts the rail back to episodes; `<Esc>` pops the drill (§R2).

* What it prints does not change: `fathom_analyze::queue::retrospect`'s rollup — what was dismissed,
  by whom, under which reason, over what coverage denominator — and the honesty rule moves verbatim:
  an unreadable ledger prints its complaint and the "nothing dismissed" line is withheld
  (`retrospective_lines`'s rule, `an_unreadable_ledger_is_said_rather_than_shown_as_a_clean_sheet`).
  Saying nothing was written this session is the line that makes the pane worth opening.
* The deep form stays the verbs' — `fathom review list --state dismissed`, `fathom review status`,
  `fathom review verify` — which is §5.1.1's two-depths rule restated for the audit trail rather
  than for a score. `QueueRetrospective` and its friends on the insight facade get renamed to what
  they are (`e10.3`), and `tools/check_delta_compat.py` is consulted before the schema moves, so a
  removed figure is a version bump and not an accident.
* **This is not the queue coming back.** The rail's ledger state is not a second ordering of the
  same episodes; it is a different subject with different rows, a different count and its own
  denominator. What the queue was guilty of was showing one set twice under two orderings.

**5. What the risk score is now, said plainly, because docs and tests assert the old framing.**

* It stays exactly what [the risk page](../concepts/risk.md) defines: a per-episode 0–100 figure with a named
  model, capped components, its reasons and its counted ceiling — printed on the row, explained in
  band 4, expanded by `w`, rendered whole by `fathom why`. `e9`'s one-figure-one-string rule is
  untouched, and no part of the arithmetic moves in `e10.3`.
* What dies is the ranking as **the ordering principle of a view**. `queue-1` (risk × staleness ×
  blast radius) goes with the pane, taking `rank_queue`, `QueuePolicy`, `QueueRanking` and
  `QueuePlacement` with it, and it takes `rank N of M` off the card: a place in a set nothing ranked
  is not a fact, so `RiskView::rank`/`ranked` go too, since the CLI scores one episode and the pane
  no longer knows a ranked set (§7.10's rule with a figure that cannot be cited). **§5.1.1's band-4
  row — "the vector, with its place" — and its question, *why is this one in front of me?*, are
  superseded here**: the band answers *what is this number, and why*, `w`'s label becomes
  *Why this score: every reason and the whole ceiling*, and the band keeps its `rank` id in code
  until a ticket renames the id and this table in one commit (`crates/fathom-tui/tests/episode_card.rs`
  reads the ids out of this page).
* Staleness is not deleted, only un-multiplied: the rail's age column is the same fact in plainer
  clothes, and `days_unread` stays a thing the reviewer can read per row. Anything that quoted
  `queue-1`'s `S` factor quotes the age instead — the risk page's *Breadth, and ties* and its
  `queue-1` record are where that gets said.
* The model name stays on screen (strip part 4). A score with no named model beside it is the
  recommendation ADR-001 §7.9 forbids.

**6. The author-kind decision, in three parts.**

**(a) The printed label goes away — everywhere a human reads it.**

| surface | today | after `e10.4` |
|---|---|---|
| rail row | ` {:<5}` author cell, the ladder's `NoAuthor` rung | cell gone, `NoAuthor` stops being a rung, `Columns::for_width`'s thresholds move by the freed cells |
| card | the attribution line `4 commits · agent 0.94 · 0:12 ago · unread` | `4 commits · 0:12 ago · unread` — commit count, age and state are not the label |
| ambient glance | `latest e8f1a2 · agent · 0:12 · risk 82 ✱ high · unread` | the author word gone; the line gains nothing, its 40-column budget is already spent on the four facts the reviewer acts on |
| `fathom show`, `fathom episodes` | a `human`/`agent` column | gone from the human-facing table; `--json` keeps the field (part (b) below) |
| any `--plain` frame that prints it | prints it | does not |

The freed six cells buy back **rungs, not content**: after `e10.4` the rail keeps its sparkline and
its time-of-day at terminals six columns narrower than today. They are not a windfall. The rail's
identity floor, the view's `min`/`floor` in §3 and the card's row budget (§5.1.1 rule 4) are not
re-opened with them — a rail column and a card row are different currencies, `e8.6`'s complexity
figure spent the card's, and `e10.4`'s own ticket says the three of them must not each assume they
own the space. If it wants more than a rung, it comes back to this page.

*As landed (`reco-ydek.4`).* The thresholds moved by exactly what the cell cost and nothing else moved:
`for_width` is 34 / 28 / 26 / 22 where it was 40 / 34 / 32 / 27 / 22, `NoAuthor` is gone from
`Columns`, and the 18-column identity floor is untouched, so a 40-column pane draws two rows of it and a
38-column pane draws two where it used to draw one. The glance line and the card print no author word, and
`fathom show` prints evidence where it printed the verdict. One thing decided here was out of this
ticket's reach and was not skipped silently: a store written while `kind=` was a dimension still names a
constraint the reviewer set, and `Filter::decode` dropping unknown keys would have dropped it quietly — so
`filter::retired_keys` names it on the resume toast instead, in the same breath as what *did* come back.

**(b) The datum stays, and the filter does not.**

*The datum*: `episode.author_kind`, its confidence, its evidence list and its reason keep being
written by `e4.1`'s ladder, keep being user-correctable, keep being what ADR-003 §8 H5's boundary
rung reads, and keep appearing in `fathom analyze --json` and `fathom show --json` as an attribution
claim with its confidence and its evidence beside it. Killing the badge is not killing the evidence:
the rung ladder is a real instrument, and `unknown`, a correction and a `via=harness` are load-bearing
for segmentation, for re-link and for the calibration work in
[false-positive-calibration](../concepts/false-positive-calibration.md).

*The filter*: **the rail's `kind=` dimension is retired** by `e10.4`, along with `Dimension::Kind`,
the editor's kind toggles, the `kind=` segment of the filter summary and `timeline.members`' `kind:`
prefix. The rule at the top of this section decides it, and three concrete miseries confirm it: a
rail filter cannot carry a confidence, so the only way to offer the narrowing is to print the words
`human`/`agent`/`unknown` in the `F` editor — re-printing the label this epic retires, in the one
surface where it would be asserted with neither confidence nor evidence; a query returning 300 rows
asserts *300 is the number of human-authored episodes*, which the rung that says `human` because
nothing said otherwise cannot support; and a row with no positive claim satisfying the kind filter is
the same inaccuracy relocated into a query, which is not an improvement on printing it. (The epic's own
wording called that case `author=human`. Named properly: the token spelled `author=` matches a git *name*
and is not the thing being retired — see the two survivors below — and the retired narrowing is the
author-**kind** one, which the rail's strip spells `kind=`.)

Two things survive and must not be deleted by a tidy hand:

* The rail's `author=` and search's `author:` tokens match the git **author name**, which git
  records rather than infers. Nothing in this epic touches them, and a child that removes one has
  removed the wrong thing.
* `fathom episodes --kind` survives on the CLI, because the machine channel is the exception the rule
  names: there the rows ship their confidence and evidence beside the claim, so the consumer decides
  what a 0.50 claim is worth. `unknown` never satisfies `human`, as today.

And the buy-back has a shape, recorded in §11: a narrowing may come back over *evidence*
(`via=harness`, `via=trailer`, `via=correction`), never over the collapsed verdict, and only with the
excluded count printed beside the selected one — `no claim: 61` on the same line as the rows it did
not pick.

**(c) The risk component is retired later, and may not go quietly.**

*As landed (`reco-ydek.5`).* The ordering constraint is what was recorded here, and `e10.5` honoured
it: the label went in `e10.4` with the component still named in the printed vector, and the component
and its name left together in `e10.5`. **`COMPONENTS` no longer spends anything on `author`** —
`spine-2` became `spine-3`, five components and a ceiling of 92 (`spine-3 92 = surfaces 50 + complexity 12
+ size 12 + deletions 10 + breadth 8`, the caps summing to `SCORE_CEILING` rather than to 100), and the
freed 8 were **deliberately not redistributed**, because a
removal that quietly re-inflates the other caps is the same trick in the other direction
(`risk::score`'s own comment says so). `features-2` became `features-3`: twelve axes, and the author
axis's `0.04` was paid to `findings` and `surface` rather than dropped, which is a redistribution and
is stated as one. Every printed surface carries the new string (rail cell, card band 4, `fathom why`,
the `--plain` frame), the G3 harness was re-measured against the pinned corpus with `--check` rather
than re-stated by hand, and authorship is now a printed blind spot on both models — a reviewer reading
the blind spots learns the tool does not know who wrote this, which is the truth the badge was
covering for.

The reason the ordering mattered, kept here because it is the rule and not the history: **the
component may not be struck from the printed vector before the points go.** A vector *is* the
explanation of the number, and a vector whose spelling hides a live component is precisely what
ADR-001 §7.9 forbids — which is why `spine-1 … + author 8 + …` kept the word for exactly one ticket's
span, and why the risk page's component table carried that row as *retiring* until it was gone rather than
pretending the table was stable.

**7. The migration story: a store written with the queue must still read correctly.**

* **No migration, not even a rename.** `triage_event`, `review_state` and `ledger_entry` are tables
  about *acts* and their names say so; the queue was a pane over them. `SCHEMA_VERSION` does not
  move, so a store written with the queue opens in the build without it, and one written without
  opens in a rebuild of a binary that still has the pane. A table rename is the one temptation here
  and the answer is no: a rename is a migration, a migration is a way to lose somebody's history,
  and "it is only a name" is what every data-loss migration says about itself on the way in.
* **An act's stamped risk is history and is never recomputed.** `triage_event.risk`/`risk_model`
  (written at the moment of the act, `record_for`) keep saying `spine-1` after `e10.5` changes the
  vector. Re-scoring the past to make an old sign-off read better is the audit trail lying about
  itself.
* **The markdown ledger is the record; the pane was not.** `.fathom/reviews/` and its four digests
  are class **M** (ADR-001 §4.6, ADR-004 §10) and nothing in epic 10 touches them. `fathom review
  sync` must still render a queue-era act as a ledger entry and stay re-runnable at `ledger_clock`
  resolution — that verb is the check that an act written by a deleted pane is still a legible act.
* **Session state degrades with a warning, never silently** (session-state §1's total decoder), for the
  retired `queue` tab view and the retired `kind:` filter members alike.
* **"Nobody's sign-off becomes invisible" is checked, not asserted.** The named checks, and what `e10.3`
  shipped against each — written down rather than left implied, because a named check that quietly goes
  unshipped is worse than one nobody named:
  * `e10.3` — **shipped**: `tools/check_docs.py` carries the retired tokens this page kills (`order: risk ×

  * `e10.2`/`e10.3` — **shipped**: `crates/fathom-tui/tests/session_arc.rs` walks the arc with `t` where it

  * `e10.3` — **shipped structurally, owed as an artefact, and shipped by `reco-o884`**: the check is

**9. The two rules that keep this from coming back.**

1. **A view is a question, not a place.** §4 says a pane that cannot be tied to its view's question
   should be a drill. The queue is the counter-example one level up: a *view* whose question is
   another view's question in a different order is the same defect, and two orderings of one set is
   one question asked twice. A new view must name, in §4's table, a question no existing view
   answers — before it gets a pane.
2. **A datum a human is never shown may not decide what that human sees.** The options for such a
   datum are the machine channel, where the confidence travels with the claim, and the blind-spot
   list, where the tool says it does not know. "It steers the screen from a column nobody reads" is
   not on the list, and it is the option every future ticket will be tempted by.

risk. They drop in a fixed order when narrow — **complexity Δ, then sparkline, then relative time to
date-only, then the risk number before the risk glyph** — and the glyph survives last because it is the
only one that also encodes *state* under `NO_COLOR` (`e5.6`). That order is `Columns::for_width`
(`timeline/render.rs`): complexity is the first surrender because a rung that cannot pay for both the
delta and the sparkline that separates it from the size column sells the delta (ADR-007 §10.1), and
there is no author rung to sell at all since the cell left the row. Selection follows
episode identity (`e1.3`, ADR-003), so a re-index mid-scroll leaves the highlight where the reviewer
put it instead of jumping to another episode.

Complexity Δ is the first *figure* to surrender, and the justification is that it is the only figure on
the row another pane in this same view carries with more room to explain it: `e8.5` put it on the card
next to the word and the coverage, and `d` carries it per file (`e8.6`). Size is what a reviewer
navigates a timeline by and no other pane of this view lists it per episode; risk is *why* the row sits
where it sits in the queue; state is the reviewer's own act (§5.4). Losing those three would leave a rail
that cannot answer "what, how big, why now, have I read it"; losing the Δ leaves a rail that answers all
four and sends the one question it gave up to the pane that proves it. ADR-007 §10.1 is what makes the
column legal here at all: it prints the **delta** (signed, so it is never mistakable for a count) in a
column separated from `+adds −dels` by the sparkline's cell, and the rail's floor form is `~+6 (2/5)`,
which says *at least* and *how much was counted* rather than being a bare number.

A row that lost the column prints no `?`. Absence of the column and an unmeasurable file are different
claims (`e8.3`, ADR-007 §7), and a surrender order that silently deleted a column would be the second;
so the rail's strip says which happened — `complexity Δ is not drawn at this width` while the ladder
holds the column out, `complexity Δ dropped to fit this row` when a particular row spent its last cell on
something else. Where the column survives it prints the same `+6` / `−3` / `±0` as every other surface,
and the two states that are not figures at all — `~` before a floored figure, `?` where the analyzer
could not count the file — are glyphs and digits, never a hue (`e8.1`).

The age column has four spellings and no zero among them: `<1m` below a minute, `h:mm` below a
day, `2d4h`, then `3mo`; a row dated ahead of the frame reads `ahead` rather than a clipped
`0:00`, because an age cannot be negative and the column must not imply one has happened
(**reco-5oe**). It is measured against the frame's one wall-clock read (ADR-002 §4.4), which an
interactive loop carries forward on the monotonic clock it already owns and re-draws on only when
the instant crosses a minute — the finest change that column can print, and so the finest one §0.1
allows a frame for. A one-frame render is that single read and nothing else, which is what keeps §6.7's
piped output reproducible.

**Amendment (`reco-8bx`, the second half of `e5.1`): the same view as a process.** `fathom ambient` is
§5.7 drawn by a program whose only job is to be open in the other terminal — no tab bar, no frame, no
session to restore, and nothing to do but answer *is there anything I need to look at right now* until it
changes. It keeps this section's contract and adds four of its own. **It is tickless in the §0.1 sense**: it
blocks for one poll (400 ms by default), reads the cheapest facts it can — a `stat` of the store, the
watcher's heartbeat, `HEAD` — and opens the index only when one of them moved, then draws **only if the text
it would print has changed**; ages are bucketed (`now`, `<15s`, `15s`, `1m`) so a repository with nothing
happening in it does not redraw once a second to say the same thing. **Its cost is a checked number, not an
intention**: `fathom ambient --self-check` prints polls, draws and the run's own measured CPU share and exits
**11** over a budget of 1 % of one core, so "it goes quiet" is gated in CI rather than claimed here.
**`<Enter>` is a handover, not a navigation**: the pane exits, names the episode it was showing, and the full
view is opened in the same terminal through the session's own resume door (`tui.view`, `timeline.selection`),
which is also how a `--root` other than the working directory keeps its identity across the keypress.
**And its refusal is drawn, not fatal**: below 40×3 it prints `AMBIENT REFUSED — TOO SMALL`, the size it
needs and the verb that works at any size, and exits **0** — the reviewer made no mistake, and a pane that
tried to draw 80 columns of fact into 30 would be the lie this ADR refuses everywhere else (§6.6).
The machine form follows §6.7 rather than inventing one: `--once` prints the pane as text and the exit code is
the answer, `--json` streams one `fathom.cli.ambient/1` object per change — the same object-per-change shape
`fathom watch --json` uses — and `--plain` means the same thing here as it does everywhere else.

a reviewer reads them, so this is where they are written):

| Token | Means | Notes |
|---|---|---|
| `author:` | who wrote it | substring, case-folded |
| `since:` / `until:` | on or after / on or before a day | `7d`, `yesterday`, `2026-03-01`; a day is a local midnight, never a millisecond window (`until:2026-03-01` includes that day) |

| `kind:` | `episode`, `path`, `dependency`, `finding`, `symbol` | narrows the group list rather than the score |
| `path:` | touches this path | also matches the row's own name, which is what a path row's name is |
| `dep:` | depends on this package | |
| `finding:` | raised this finding kind | |

build cannot honour is a fact about the build, and `fathom` says which. A filter that narrows
nothing at all is reported with its count (`2 of 0 candidates`), because a filter that silently
did nothing is a query whose answer was never about the repository.

**Where the code is.** The corpus, the scorer, the filter grammar and the report are
`fathom_analyze::search` (with `search::score`, `search::query` and the store read in
`search::corpus`); the symbol section is filled by `search::symbols`, which asks `fathom_ingest::worktree`
for the working tree and hands what comes back to the structural extractor of `e3.1` under stated caps —
the analysis crate is IO-free (ADR-002 §3, lint `W1`), so the walk that opens the directory lives at the
door — because a declaration is a function of the tree and not of an episode; the recent and saved searches
are `search::history`, which is deliberately
not a store read so a backend-less binary still remembers what the reviewer was asking. Every corpus
carries the identity it was read from — the store's index epoch and the tree the symbols came from — so a box
that stayed open while the repository moved says so instead of answering from rows the repository has already
replaced. The overlay, its deep links and its rows are `fathom_tui::search`, and the corpus itself is read by
`fathom-cli`'s `search` module at startup and handed over — the shell scores what it was given
and never opens a store (§1 R3, ADR-002 §5.2). The latency promise is ADR-004's
`query.search.ms` (p95 50 ms), measured by `fathom-analyze`'s `tests/search_scoring.rs` on a
ten-thousand-episode corpus, over this same call path — with ADR-004 §11.8's runner factor as headroom,
because that test measures the debug build on whatever runner CI happened to hand it (`reco-cqwz`).

## 6. The degradation contract

The brief asks for "one degradation order per view". This section instead defines **one
ladder for all views**, applied in a fixed order until the view fits, and then *derives* each
view's order from the steps that fire for it. A per-view hand-written list would have been
eight documents that disagree with each other the first time a pane width changes.

### 6.3 Width and height are different problems

Rows degrade by **removing** lines in importance order (§1 R3). Columns degrade by
**narrowing** panes and then by dropping *columns of a row*, in a fixed order per list:
sparkline, relative-time→date, author, then the risk *number*, and finally the risk *glyph*
last of all (§5.2). Diff hunks never drop a column: they truncate the line and print `…`,
because a silently truncated diff line is worse than a visible one. The diff's split view is
opt-in and degrades to unified below ~100 columns rather than clipping a side.

### 6.4 Announce, every time

Dropping content silently is the one failure ADR-001 §7.2 says a review tool is not allowed.
So a degraded frame says so, and the notice **leads** the status line — the status line is
the last chrome standing and the first thing to be truncated, so a notice that could be
clipped away would be the same hidden suppression in a nicer font. These two frames are
rendered by the same code `e5.5` will ship, not typed here:

### 6.6 Below the floor: fall back, then refuse — both stated

Below a view's **floor**, `D9` gives the secondary panes back to the primary pane and the
status line names what left the frame; the content is one `<C-w>l`/`<Enter>` away and the
selection is preserved. Below a view's **refuse** size the view is not drawn at all:
`e1.5` shows a refusal panel that states the size needed, the size it got, the key that
switches to ambient (which fits 40×3), and `fathom --plain` for a text render (`e5.5`).
Drawing a 9-column treemap would be the failure; saying "I cannot draw this here" is the
correct answer to a question the terminal cannot ask.

The panel is `fathom_tui::frame::refusal_panel()`, and it is drawn by the same code that drew
§6.4's notices, because "reported, not silent" has to survive being read. Two things about it
are testable and tested rather than left to review: the width budget (`f "need {want}×{h}, have
{w}×{h}"`, the widest line in the panel, sets the floor's width, so the message cannot be the
reason the panel does not fit), and the ordering — what a `d` on a 25×12 terminal *becomes* is
exactly the sentence an operator needs before reaching for a key.

### 6.7 Non-TTY and pipes

No terminal at all is not a degradation, it is a different contract: `--plain` prints ordered
text with no escape sequences (`e5.5`), and every view has a headless equivalent through the
CLI verbs (`e1.10`). The refusal panel is for a real terminal that is too small; `--plain` is
for no terminal.

Two panes side by side is the right shape for eyes and the wrong shape for anything else, so
`--plain --lines` prints the same frame in **reading order**: one block per pane, each block
headed by the pane's own name and position (`▸ worklist · e4.5 · pane 1 of 2`), with no column
rules and no clipping to a column's width — a `reads …` line that the grid had to ellipsize
arrives in full. Same facts, same order, one per line, which is what makes it usable as a log
and what a screen reader expects. `crates/fathom-cli/tests/tui_text.rs` pins the three claims
that can be checked from outside the process: no `\x1b` reaches stdout, no column rule survives
in the line mode, and every row the grid drew is in the line mode (allowing it to be longer).

The facts about the terminal — `TERM`, `COLORTERM`, `NO_COLOR`, the locale chain, tmux, screen,
ssh, whether stdout is a terminal at all — are gathered by the CLI into a
`fathom_tui::terminal::Probe` and *passed in*, because `fathom-tui` does not read the process
environment (ADR-002 §5): a library that reads `TERM` cannot be driven from a test, a daemon or
a MCP server. `Probe::notices()` is the list of degraded answers, each naming the remedy, and
the CLI prints them on both paths — to stderr under a TUI, to stderr beside the text on a pipe.
A healthy terminal gets none: a wall of caveats trains the reviewer to skip the one that matters.

### 7.0 The four rules

| # | Rule | Why | Checked by |
|---|---|---|---|
| **K1** | Every action is bound in some mode **or** is a palette entry. The palette is a keyboard surface, so "palette-only" is still reachable. | "Everything reachable from the keyboard" has to be a property you can enumerate, not a hope. | `test_every_action_is_bound_or_in_the_palette` |
| **K2** | Every mode's bindings are checked against the action registry: an action bound in a mode that does not accept it is a startup error with the file and line to fix. | `keys.overrides` is user input, and a silently-ignored override is a user who believes a wrong keymap. | `test_conflicts_are_reported_not_absorbed` |
| **K3** | Each of the eight frame views is one letter on the home row neighbourhood, and those eight letters plus `/`, `,`, `?` are reserved globally. | Muscle memory is the whole point of a keyboard-first tool; two letters per view would double the sequence length of every task in §9. | `test_view_keys_match_the_view_registry` |
| **K4** | A view or interaction mode may never shadow a globally reserved key. | `p` inside the graph canvas must still mean "go to deps". A view that eats its own navigation keys is a view with a maze in it. | `test_no_mode_shadows_the_globally_reserved_keys` |

### 7.1 Mode model

`MODES` and `PRECEDENCE` are in §1.1. Two consequences worth stating: the same chord can mean
different things in `list` and `body` (`j` moves a selection vs scrolls a document) and that
is *correct*, because the pane type is the mode; and the two exclusive modes mean a text
field is a genuinely different instrument, not a filter that happens to eat some keys.

**Text means every keystroke the mode does not bind, the space bar included.** The terminal does
not deliver the space bar as a space: it arrives as the chord `<Space>`, and a runtime that
decides "printable" by counting one character excludes it. The consequence of getting that wrong
is total rather than cosmetic, because the query grammar (§5.2) is token-based: a field that
eats the space cannot express `risk>60 author:dana`, let alone the free text that composes with
it, and it then saves the mangled result as what the reviewer asked for. `keymap::text_of` is the
one place that answers "is this chord text?", and the published table (§7.3) binds no action to
bare `<Space>` in `prompt` or `pick` — the space bar is not a key to spend, so nothing has to
choose between the field and an action. (`<Space>` is `list.expand` in `list`, where no field is
holding the keyboard; an override may still spend it in an exclusive mode on an action that mode
is allowed to bind, and then it is the reviewer's own space bar they spent.)

### 7.2 Motion conventions

One implementation (`e5.4`'s AC: "motion behaviour is identical across timeline, file tree,
queue and search results"), bound once in `list`, mirrored in `body` for scrolling, and bound
on the arrow keys as well (`ALIASES` in `keymap.py`; the aliases are bindings, so the
cheatsheet prints them and the test counts them).

```
j / k            one row down / up                <Down> <Up> are the same bindings
H / M / L        first / middle / last visible row
gg / G           first / last row
<C-d> / <C-u>    half page down / up              <C-f>, PageDown, PageUp: full page
<Space>          expand / collapse a node         (tree, treemap, transitive tree)
n / N            next / previous match            (search results, filter hits, changed nodes)
<Enter> / <Right>  drill in                       <Esc> / <Left>  up one level
<Tab> / <S-Tab>  focus next / previous pane      <C-w>h / <C-w>l the guaranteed route
```

What vim does *not* get here, and why: `d`, `x`, `s`, `p`, `a`, `f`, `c`, `m`, `y` are Fathom
verbs (view, reviewed, structure, deps, ambient, flag, compare, mark, copy), so vim's delete,
paste, append, substitute and yank are unavailable by construction. `gt`/`gT` cannot exist
either, because `g` is the graph view and a `g` that waits for a second keystroke would make
the graph key feel broken; tab cycling is `J`/`K` (plus `<C-w>n`/`<C-w>p`, `<C-w>1..9`, and
the palette). This is recorded here precisely so `e5.4` does not relitigate it in a comment
thread at 01:00.

**A held key says so.** `g` is `view.graph` and `gg` is `list.first`, so a lone `g` cannot be
answered until the wait for the second key expires — `CHORD_TIMEOUT`, 250 ms. The cost is
accepted above; what is not accepted is paying it silently. A reviewer who presses `g` and gets
back the same screen presses it again, and the second press is `gg`: a different action, in a
different mode, in a view nobody asked for. So the frame a chord lands on says a chord is in the
air — on the hint row beside the key hints, or on the status row wherever there is no hint row to
borrow (glance has none, and neither has `ui.hints = false`). The line names the key held, what it
becomes if nothing else arrives and how long that will take, and what a second key could still make
of it, all three read out of the merged table so an override cannot make the frame lie about it
(`reco-wlt`). The wait is not shorter; it is no longer invisible. And ambiguity is measured in
keystrokes, not characters: `<` is the first *character* of every named chord and the first
keystroke of none of them, so `<` answers at once and `g`/`gg` stays the one ambiguous pair the
table ships — which is what the paragraph above asserts and what `pending_chord.rs` now measures.

### 7.5 The palette and the hint line

The palette (`,`) is the *command* surface: it enumerates `palette_entries()` with each
action's current binding shown beside it, so a user who rebinds `x` sees the new key the
moment the merge happens. Completeness is enforced, not asserted: a new action that is neither
bound nor palette-listed fails CI.

has stopped needing it:

A toast borrows that row; it never owns it. An act's report — what was marked, what was
copied, why a refusal refused — is drawn in place of the hints for `TOAST_LIFETIME`, six
seconds of wall clock, and the frame that gives the row back is drawn whether or not a
keystroke caused it. The lifetime is a clock and not a number of draws because the loop is
tickless: a draw happens when something changed and otherwise nothing is drawn, so a toast
that aged one tick per draw expired only on the next press and never at all on a frame that
had gone quiet — which is the hint line evicted for the rest of a session, from one dismissed
help overlay (`reco-2ll`). The two are never side by side: while a toast is live it *is* the
row, and a reviewer who wants the hints back has nothing to press for them.

A chord in the air outranks a toast, but only for the length of the wait. A toast reports an act
that is already over; a held key is the question being asked right now, and answering it is what
the row is for (§7.2). The loan is still a loan: when the chord resolves to something that prints
nothing, the toast that was there before is back, on its own clock (`reco-wlt`).

### 7.6 Retirement: what a key means when its surface goes away

A keymap is a published contract, so unbinding a key is a change to it rather than a cleanup,
and the two rules that make that survivable are these:

* **delete the action, or keep the key — never unbind and keep.** An action that is unbound but
  still in the registry is a palette row with no keystroke and a help overlay that lies, and K1
  is exactly the check that catches it. So a retired action leaves the registry, and takes its
  palette row, its help-overlay line and its cheatsheet row with it, all generated from the one
  deletion. An action that survives keeps a binding, in a mode that can reach it.
* **a retired letter is not free; it is §8.2's.** A key whose action was deleted joins the
  reserved-for-user set — which is the class of keys *Fathom binds none of and the next ticket
  may not take*, which is exactly what a retired letter is. That is the difference between "the
  user may have it" and "the next ticket may have it", and it makes the retirement visible in the
  generated table rather than in a commit message. Rebinding a retired letter in the default table
  needs an amendment here, naming the question the new binding answers — the same bar `gt`/`gT` face
  in §11. A retired letter outside K3's globally reserved set (the eight view keys, `/`, `,`, `?`)
  touches no navigation, which is why retiring one is possible at all.

`e9.1` (`reco-5js3.1`) is the first instance, and §5.1.1 is the decision: `intent.show` is
**deleted** with the intent pane, so `i` becomes a reserved-for-user letter and the default
build binds nothing to it; `risk.explain` **survives** with a changed job (expand the ranking
band in place, §5.1.1), so `w` keeps its binding, its palette row and its hint-line seat and
only its label moves. Nothing else in this keymap is retired: every *other* row of §7.3 keeps
both its key and its meaning, unchanged, until `e9.3` lands the two changes above.

**`e10.1` (`reco-ydek.1`) is the second instance, and the first where a whole view is the thing
deleted (§5.1.2).** Three actions, three fates, all of them the rules above applied:

| action | fate | key |
|---|---|---|
| `view.queue` | **deleted** — the view, the worklist and the palette row go with it | `q` joins §8.2's reserved-for-user set; the default build binds nothing to it, and §11 carries the bar for taking it back |
| `queue.retrospect` | **survives, renamed `review.retrospect`**, because the audit need survives and only its host dies | `r`, moved from the dying `queue` mode to `global`, where it was bound nowhere else — so no key is spent and no key is stolen |
| `review.accept` / `.flag` / `.dismiss` / `.snooze` | **survive unchanged** — id, key, mode. They were `global` bindings addressing `App::act_target`, which already resolved to the rail outside the queue | `x` `f` `-` `z`, unchanged; what changes is which pane owns the feedback (§5.1.2 §2) |

`w` survives twice over: it keeps its key through `e9.1`'s change *and* through `e10.3`'s, and only
its label moves again ("why this rank" → "why this score", §5.1.2 §5), because the model-owned
string that promised `w` lists the blind spots is still true.

## 8. Chords: what the terminal cannot deliver, and what Fathom refuses to bind

Two different lists, and conflating them is how a keymap ends up with a binding that works on
the author's laptop. The first is physics; the second is a promise.

### 8.1 Measured delivery

`python3 -m recommender.tui probe` opens a pty, sets it three ways, and reads what a program
would actually receive: `raw` (crossterm's raw mode), `fathom` (raw **with `ISIG` left on**,
which is the mode this ADR commits to so that the exit and panic hooks own terminal
restoration — `e1.5`'s "Ctrl-C or a panic never leaves the terminal in alt-screen"), and
`cooked` (the inherited default flags: canonical, `IXON`, `ISIG`).

Measured on this container (Python 3.14, `/dev/ptmx` present, `ISIG`/`ICANON`/`IXON`/`ICRNL`
all on by default, `VERASE=0x7f`, `VKILL=0x15`):

| Claim | Result |
|---|---|
| Ctrl-I and Tab are one byte | **confirmed** — `0x09` in all three modes |
| Ctrl-M and Enter collide once `ICRNL` maps CR→LF | **confirmed** — `0x0d` arrives as `0x0a` in cooked mode |
| Ctrl-C / Ctrl-Z / Ctrl-`\` are signals, not bytes, when `ISIG` is on | **confirmed** — no byte reaches the reader in `fathom` mode |
| Ctrl-S / Ctrl-Q are flow control while `IXON` is on | **confirmed** in cooked; Fathom turns `IXON` off, so they *are* deliverable and are simply not bound |
| Meta/Alt is `ESC` + key | **confirmed** — `A-x` arrives as `0x1b 0x78`, i.e. `Esc` then `x` |

Measured again in `e1.5` (`reco-v6t`), because the mode Fathom takes is crossterm's, not the
probe's: crossterm 0.29's `enable_raw_mode` is `cfmakeraw`, and `cfmakeraw` clears `ISIG`. On the
shipped path `<C-c>` therefore arrives as the byte `0x03` and `app.quit` is reached as the binding
the published table says it is, while the `SIGINT`/`SIGTERM`/`SIGHUP` flags and the panic hook are
the second door rather than the only one. Both are tested
(`crates/fathom-tui/tests/terminal.rs`), and neither the promise of this section — Ctrl-C never
leaves the terminal in alt-screen — nor `<C-c>`'s immunity to rebinding depends on which door a
given terminal uses: a terminal that keeps `ISIG` on, including the probe's `fathom` mode above,
is served by the signal path instead.

| **reserved for user override** | q | a byte, simply unbound | all modes | the Queue view's letter. `e10.3` retired the view (ADR-006 §5.1.2 §1): the timeline is home and `t` stays the home letter, because a key belongs to the view it opens and not to the pane that happened to be deleted. The acts moved to the rail and `r` came with them, so nothing this build needs is spelled `q`. Free for a chord of your own; §11 carries the bar for binding it in the default table again. |
<!-- END GENERATED: reserved-chords -->

Two decisions come out of that table. First: **no Alt/Meta chord is bound in v1**, because
`Esc` is the most important key in the keymap and an Alt chord would spend it twice.
Two-keystroke chords (`<C-w>l`, `gg`) are the escape hatch and cost nothing to deliver.
Second: **`<C-c>` is the only quit key**, and it is not a binding at all — `ISIG` stays on so
the panic/exit hook is the thing that restores the terminal, which is exactly what `e1.5`'s
acceptance criterion tests.

### 8.2 Reserved for user override

The first class in the table above is physics. The second class is this ADR keeping keys free
for the user: `<C-a>`, `<C-b>` (tmux and screen prefixes), `<C-e>`, `<C-g>`, `<C-k>`, `<C-n>`,
`<C-t>`, `<C-v>`, `<C-x>`, `<C-6>` and `<S-F1>`. Fathom binds none of them in v1, and `e5.4`
may not "convenience" one later without amending this ADR: the value of a reserved chord is
that a user's `.fathom` config does not break on a minor release.

### 8.3 Overrides, and the merge order

`fathom.toml` carries `keys.overrides.<mode>.<binding> = "<action-id>"` — the `e0.8` key spec
already declares it, and `e0.8` explicitly **refused** a `[keymap]` section that could own
bindings, because the canonical table is this ADR's. Setting a value to `""` or removing the
key unbinds. `keymap.merged()` is the merge, `keymap.conflicts()` is `e5.4`'s startup check,
and the four failure modes it reports are: unknown mode, unknown action, an action bound in a
mode that does not accept it, and a shadowed navigation key (K4). All four are reported at
startup with the offending `file:line`, which is what `e0.8`'s `config explain` machinery
already knows how to produce.

The line is found by reading the file's own text, not the parsed document: `toml_edit` 0.25 hands out
no spans for keys parsed from a string, and a refusal that names the wrong key but no line sends the
user hunting. The lookup is the one a person would do — find `[keys.overrides.<mode>]`, then the
`chord = …` line inside that section — and an override written any other way (an inline table, a
dotted key) is reported with no line rather than with a wrong one. A refused override is *dropped and
said*, never applied: a keymap that half-loads is a keymap whose cheatsheet lies.

`fathom tui conflicts --toml fathom.toml` runs the same check on a file; `--set` is for
one-off questions.

## 10. Mouse, colour, and copy rules that fall out of the layout

### 10.1 Mouse is additive, and only additive

Click selects and moves focus; double-click drills; the wheel scrolls the pane under the
pointer; a pane border drag resizes. Nothing exists only on the mouse, which is checkable in
one sentence: the mouse issues the same actions as the keyboard, so the action registry is
also the mouse's contract, and `e3.4`'s "fully keyboard operable and consistent with the
ADR-006 keymap; mouse is additive" is that sentence made a ticket.

**Capture is opt-in, because the cost is real.** `fathom tui --mouse` takes the pointer; without
it, mouse reports are never enabled, because the instant the terminal starts reporting motion
the terminal's own text selection stops working — and copy is how a reviewer gets a path out of
`fathom` and into a comment (ADR-004 §9). The status line says `mouse on` while it is armed, and
`--plain` refuses it with a sentence rather than ignoring it. `App::pointer` is the whole
implementation, and it is written as a *translator*: a click becomes `Motion(row)`, a second
click in the same cell within the double-click interval becomes `Activate`, the wheel becomes
`Scroll(...)`, and nothing else exists. `crates/fathom-tui/tests/pointer.rs` is the parity
check in the form the claim allows — it applies the gesture and the key to two identical
shells and asserts the resulting state is byte-identical, for every gesture, and that the
keyboard alone reaches every action the pointer can reach. A gesture that lands on chrome
answers in words instead of doing nothing, which is the same rule §6.4 applies to a degraded
frame: an input the terminal cannot honour is a fact the reviewer is owed, not a silent drop.

### 10.2 Colour never carries a fact alone

Risk, added/removed, and violation states each ship a glyph and a text label next to the
colour (`e5.6`'s `NO_COLOR` and colour-blind criteria). This is a layout constraint, not a
theming preference: the glyph is part of the width budget in §5, which is why every pane
table in §5 lists the glyph columns explicitly and why the risk *number* is dropped before
the risk *glyph* when a list gets narrow (§6.3).

Because §10.2 holds, `NO_COLOR` is allowed to be a subtraction and nothing else:
`fathom_tui::style::strip_colour` is the single place a colour is removed, applied at the sink when
the probe answered none. The frame is laid out identically, every glyph, rule and marker stays, and no
cell is painted. `crates/fathom-tui/tests/termenv.rs` checks that by reading the painted cells back
off a real sink, because "the flag is plumbed" and "the flag changes what the terminal is given" are
different claims.

`e5.6` (`reco-2fv`) made the other half of §10.2 measurable, and moved "the single place one is
chosen" from `Face::style` to a **`Theme`**: a view names a face (`Face::Added`), never a colour, and
a test fails the build if a `Color::` literal or a hex appears outside `theme`/`colour`. Built-in
`dark`, `light` and `ansi` are each audited — every face against the ground it is seen on at 4.5:1
(6.0:1 when dimmed), and the added / removed / violation pairs at ΔE ≥ 14 under simulated protanopia
and deuteranopia — with `fathom tui --show-theme` printing the measurements and `--audit` exiting 7 on
a failed floor. Selection is `--theme` > `$FATHOM_THEME` > the *user's* config, and a repository's
`fathom.toml` is deliberately not a layer: a clone does not get to repaint a reviewer's terminal, for
the same reason ADR-001 §4.6 does not trust a clone's consent config. [Theming,
colour-blind safety and colour that is not load-bearing](../concepts/theming.md) is the full contract,
including the screenshot test that draws the timeline twice and asserts the two frames' text is
byte-identical — which is what §10.2 actually claims.

### 10.3 Empty, loading and partial states

Every pane has a named empty state that states the next action (`e5.9`), and every partial
result names its cause and its budget (`e1.10`, ADR-004 §7.6). The generic ones are
fixed here so the copy can be reviewed once as a batch:

| State | Printed | Why this wording |
|---|---|---|
| No index at all | ``no index here yet — run `fathom index` here, then reopen fathom`` | a shrug is not a remedy — and this one is true, because there is nothing indexed to read |
| Index finished, nothing loaded | ``index epoch 1 ready · 500 commits · 412 eps — `t` opens the timeline, which lists them as the index knows them; `fathom show <episode>` prints one in full`` | the index is already done, so the sentence this row used to carry (*run fathom index*) was a loop, not a remedy: the reviewer ran it, reopened the shell, and was told the same thing — the MVP walkthrough's second P1, closed under `e5.9`'s remit. The wording names the timeline because the composition root now reads a page of episodes out of the spine (the walkthrough's first P1): the episodes are readable in this build, and what is still missing is the delta model that ranks them |
| Index finished, nothing to list | ``index epoch 1 ready · 0 commits · 0 eps — the index has nothing to list; `fathom doctor` says whether that is the repository or the run`` | a finished index over an empty repository and a finished index that lost its episodes are different facts, and neither is a quiet repository |
| Index running | `indexing 62 % · ~14 s left (4 102 commits)` | a percentage without a converging estimate is a lie with a spinner |
| Epoch still `building` | ``index epoch 2 building · 500 commits · 0 eps — the epoch is still being written — wait for it; if a rebuild died halfway, `fathom index --rebuild` starts a clean one`` | a rebuild that died is a state with an owner, not an empty repository (`e1.4`, ADR-004 §9.3) |
| Store will not open | ``the index would not open — `fathom doctor` says what is wrong`` | "could not open" and "not indexed" have different remedies, and only `fathom doctor` may decide between them |
| Analysis unavailable | `blast radius: unknown — no graph snapshot at this tree hash` | `unknown` is a value, not a blank (§0.1) |
| Hunk text still decoding | `⋯ hunk 11 (25 row(s)) is being decoded — this window is not complete` + `2 hunk(s) in this window still decoding` | the hunk is on its way from a worker (`e1.8`); the hole sits at the row the hunk starts at so the window neither shrinks nor jumps when it lands, and nothing from another window or another shape is ever drawn to fill it |

Two rules the first four rows and the last two share, both of them learned the expensive way:

* **the index state a pane prints is the index state the caller read.** The shell has no store handle
  and may not get one (ADR-002 §5.2), so `fathom-cli` reads the epoch, its status, and the commit and
  episode counts once, before the first frame, and hands them over. A pane may not guess; guessing is
  how an index of 500 commits got told it was empty.
* **no sentence may name a command this binary does not have.** `fathom --demo` was such a command, in
  this row's old wording; a remedy that cannot be typed is worse than none, because it gets typed.

**Note added by `e5.9` (`reco-2uo`).** Both halves of that rule got built, in that order. `fathom --demo`
is a flag now: the binary carries a miniature repository, indexes it with the ordinary `fathom index`, and
opens on it, which is the one place the tour belongs in a pane — beside `fathom index` in the *no index at
all* row, for a reviewer who has not yet decided whether this is worth setting up. And the rule itself is
machine-checked: `crates/fathom-tui/tests/empty_state.rs` and `tests/empty_views.rs` hold the published
verb and flag list and fail on any pane string that names something outside it, while
`crates/fathom-cli/tests/copy.rs` reads the verb and flag lists off `fathom --help` on the built binary, so
the two lists cannot drift apart unnoticed. The same file requires every refusal to end in a next action.

**Note added after `e1.12`'s MVP walkthrough.** The rule has a second surface, and the walkthrough
found it by measuring the screen instead of reading the code: it redrew after every keystroke and asked whether
anything had changed. Eleven of its forty-one keystrokes had produced no change at all — `y`, `Y`,
`<Enter>`, `x` and `i`, all over an empty rail — while `m` and `w`, a few rows up the same table,
answered in a sentence. A pane with a named empty state beside a key that answers nothing is this
table's failure wearing a different hat, and a keystroke that cannot apply and says nothing is
indistinguishable from a keystroke the terminal lost. So §10.3 covers the keyboard as well as the
panes:

* **every bound action either changes the frame or prints the reason it could not.** The empty rail is
  the state to test in, because that is where a key has nowhere to go: `y` with no path under the
  cursor, `j` with no rows to move over, `<Tab>` in a one-pane view, `t` on the view already live.
* **the reason is the absence and then the way out, in that order** — *nothing is selected, so there
  is no path to copy — `j`/`k` choose an episode first* — the shape this section's other rows use,
  because the second half is the half a reviewer can act on.
* **two ids are exempt, by name and with a stated reason:** `app.quit`, which ends the session rather
  than the keystroke, and `screen.redraw`, for which an identical frame *is* the answer. The
  exemption is re-measured every run, so it cannot quietly outlive its reason.

`crates/fathom-tui/tests/action_speaks.rs` is the enforcement: it walks the whole registry of §7.4
against an empty model in all eight views and fails on any action that neither moved the frame nor
left a sentence on the hint row — the walkthrough's measurement made permanent, for every key rather
than the five it happened to try. A refusal an empty pane already explains does not need a second
sentence: `d` over a rail with nothing in it changes the view and the pane prints why it is empty;
`d` again, in a frame that cannot show the change, is the one that has to speak.

The loading row above is now produced rather than hand-written: `fathom_core::progress` holds one estimator
(a median rate over a window of recent samples, with the rejected alternatives argued in its docs) and prints
`indexing 62 % · ~14 s left · 4 102 / 6 552 commits` identically from `fathom index` and from the shell —
which is what "converging" was ever supposed to mean, and what `crates/fathom-tui/tests/progress.rs` asserts
against synthetic histories whose true per-unit cost is known. Its states are this table's, spelled out in
[docs/concepts/onboarding.md](../concepts/onboarding.md) §3: `estimating…` before a rate exists, `unknown %`
where no denominator does, `stalled` when the counter stops, `done` when it does not stop because it
finished. The per-pane empty states — the same rule applied to eight views rather than to the index axis
alone — live in `crates/fathom-tui/src/empty.rs`, one module, reviewed as one batch.

The loading row above is the visible half of a rule the panes are built on: **a frame is never the
frame that is waiting for a read.** Decoding is done by workers that serve the visible window before
the hunks just outside it, a hard cap bounds what may be in flight, work for a window the reviewer has
scrolled past is cancelled rather than finished, and the neighbour episode is pre-warmed so arriving at
it reads nothing. The mechanism, the caps and the four measured criteria are
[docs/concepts/materialization.md](../concepts/materialization.md); what this ADR fixes is only the
wording of the hole and the fact that a hole is drawn *in place* rather than by redrawing the pane.

## 12. Alternatives considered

* **One view with panels that toggle.** Rejected: at 80 columns, toggling panels inside a
  single view produces a frame whose meaning depends on hidden state. Nine views with a
  shared frame and a shared motion model cost the user nine keys and buy a mental model that
  fits in a cheatsheet.
* **Timeline as the home screen.** Rejected when this ADR was written, on ADR-001 §4.1: a reviewer
  arriving to 400 unread episodes needs a ranking, and chronology is not one. **`e10.1`
  (`reco-ydek.1`) reversed this** — see §5.1.2. What changed was the evidence about use, not the
  argument: the reviewer with 400 unread episodes turns out to work the timeline anyway, and the
  ranking's real value is a figure on a row, where it stays.
* **Keep the queue as an opt-in view** (`ui.home = queue`, both homes shipped, the reviewer picks).
  Rejected by `e10.1`: a per-repo fork of the view inventory forks §4's one-question-per-view rule,
  the generated inventory, the cheatsheet and both layouts, and it re-imports the defect it was
  written to remove — a second place to be is a second place to be whoever chose it. One home, and
  the letter `t` says which.
* **Keep the ranking, drop the pane: sort the rail by risk.** Rejected by `e10.1`, and this is the
  tempting one: it looks like keeping the insight and losing the chrome, and it is the queue with the
  label changed. The reviewer gets one set of episodes in a second order again; the order stops
  matching the day the work happened, which is the order the harness produced and the order an
  `orphan`/`stale` re-link can be argued about in; and the row's risk figure — which is what the
  ranking was always for — is unchanged by the move, so nothing is bought.
* **Print the author label with its confidence attached** (`agent 0.94`, `human 0.50`). Rejected by
  `e10.1` (§5.1.2 §6): the places the guess is wrong are precisely the places it prints `0.50`, so
  the correction is invisible exactly where it is needed; six columns cannot carry an evidence list,
  which is the only thing that makes a confidence checkable; and ADR-001 §7.7's `s4` update already
  ruled that a printed number is evidence to weigh rather than a probability to trust. The datum
  with its confidence ships where a consumer can weigh it — `fathom analyze --json`.
* **Vim's keymap, faithfully.** Rejected: the ticket's key list is the product. `d` is the
  diff view, so vim's `d` (delete) cannot exist; `g` is the graph, so `gt`/`gT` cannot exist.
  The motions that carry over (`j k H M L gg G <C-d> <C-u>`) are the ones that transfer to a
  read-only tool anyway (§7.2).
* **A modal editing-like command mode with `<Space>` as leader.** Rejected: a leader key makes
  every single-key binding pay a timeout, and single-key view switching is the whole
  interaction. `<Space>` is used for one thing that has no better key: expand/collapse in a
  tree.
* **Alt chords for panes (`A-1`, `A-2`).** Rejected on measurement: they arrive as `ESC` plus
  a character, so they are indistinguishable from `Esc` followed by that character (§8.1) —
  exactly the collision `Esc` (drill out) cannot afford.
* **A hand-written degradation table per view.** Rejected: the ladder is shared by eight views
  and one renderer, so the per-view order is a *derivation*, and deriving it once in
  `render.ladder_boundary()` means the ADR cannot drift from the layout engine.
* **Three panes per view at 80 columns.** Rejected on arithmetic: three panes plus borders
  leave ~24 columns each, and a 24-column diff is not readable. The third region exists, as
  a strip line inside a pane, and `D3` removes it first.
* **Deferring this ADR until the screens exist.** Rejected: it is a `decision` type for
  `e0.6` precisely because eleven screen tickets depend on it, and `e1.6`'s AC already cites
  "matches the ADR-006 keymap".

## 13. Consequences

1. **`e1.5` inherits a specification, not a suggestion.** The shell implements `MODES`,
   `PRECEDENCE`, `DEFAULTS`, `fit()` and `draw()`'s contract — same names, same precedence,
   same refusal panel. Anything else is a drift bug, and the drift is visible because the
   help overlay is generated from the same table.
2. **Every screen ticket now has a size contract.** `e1.6`'s virtualised rail, `e1.7`'s chunked
   reads and `e3.4`'s aggregation thresholds now have a *documented* size they must be legible
   at, which is what makes their performance criteria meaningful rather than decorative.
3. **The palette's completeness is now checkable**, and a new action that is neither bound nor
   palette-listed fails CI (`K1`). This is a new, permanent tax on every UI ticket and it is
   the price of "everything reachable from the keyboard".
4. **`e5.4`'s freedom is narrower than it may have expected**: the reserved key set in §7.2
   K4 and the reserved chords in §8.2 are checks, and vim fidelity is explicitly off the
   table. Its remaining freedom — override ergonomics, the hint line, which-key affordances —
   is where its value actually is.
5. **Ambient gets built early.** Because the fallback shape of every view is ambient's shape,
   `e1.5` implements the ambient renderer before the queue, which is a small reordering of
   `e5.1`'s work and the reason `e5.1` can depend on `e1.9` and `e4.5` instead of on the whole
   of epic 5.
6. **A new failure class is now visible.** "A pane shows a number it cannot cite" and "a
   degraded frame dropped something silently" are both defects with named owners (`e2.11` and
   the degrading view respectively) rather than user complaints with nowhere to land.
7. **The docs site (`e7.5`) gets its cheatsheet for free**, generated from the same table as
   the help overlay — which is the third time in this ADR that "generate it, or it lies".
